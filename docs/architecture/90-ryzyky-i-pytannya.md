# 90. Ризики, знахідки, мертвий код, відкриті питання

Знахідки з читання коду версії 78. Це **не** підтверджені баги: кожну варто перевірити
на тестовій парі баз перед виправленням.

## Надійність доставки

| # | Знахідка | Де | Наслідок |
|---|---|---|---|
| R1 | Довідник позначається «вже вивантаженим» у момент формування JSON, а не після успішної доставки й завантаження | `СМП_ОнлайнОбменКонвертацияОбъектов.ВыполнитьВыгрузку` → `ЗарегистрироватьВыгрузкуЭлементовСправочников` | Якщо HTTP-відправка або завантаження довідника в приймачі впали, наступні документи несуть лише посилання на довідник, якого в приймачі немає |
| R2 | Невдала відправка одного вихідного повідомлення не зупиняє наступні | `СМП_ОнлайнОбмен.ВыполнитьОтправкуИсходящихСообщений` | Документ може дійти без своїх довідників; порядок порушується |
| R3 | Немає автоповтору — **за задумом**: помилку розбирає людина й повторює вручну **[автор]**. Ризик лише в тому, що про нові помилки ніхто не сповіщає | усі обробники черг | Помилки помітні лише при перегляді форм черг |
| R4 | 201 від приймача = «у черзі», результату завантаження джерело не знає | HTTP-сервіс | Розбіжності між базами не видно з джерела |
| R5 | Можливе «застрягання» `Новое`: фонове завдання завершується, коли інший сеанс саме фіксує новий рядок | `СформироватьОтправитьИсходящиеСообщенияВФоне` / `ОбработатьВходящиеСообщенияВФоне` | Рядок чекає наступного запису цим користувачем **[гіпотеза]** |
| R6 | Паралельні фонові завдання на кожного користувача; порядок між користувачами не гарантований | ключ завдання `обмін/користувач` | Залежні об'єкти від різних користувачів можуть прийти в різному порядку |
| R7 | Порядок у чергах — лише за `ТаймШтамп` (мс); при однакових мітках порядок не визначений | запити `УПОРЯДОЧИТЬ ПО ТаймШтамп` | Рідкісна перестановка довідника й документа **[гіпотеза]** |

## Помилки, що губляться

| # | Знахідка | Де |
|---|---|---|
| E1 | `ВыполнитьЗагрузку` перехоплює виняток порожнім `Исключение` — помилка в `ПровестиЗаписьНеЗаписанныхОбъектов` (відкладений запис довідника) не потрапляє в `мОшибки`, повідомлення вважається успішним і видаляється | `СМП_ОнлайнОбменКонвертацияОбъектов.ВыполнитьЗагрузку` |
| E2 | Помилки вивантаження (напр. «не знайдено ПКО», код 45, помилки обробників ПКО) йдуть лише в протокол: під час вивантаження `мОшибки` ніде не заповнюється, а `ДанныеПоСсылкеВJSON_2` все одно не використовує зібраний текст. Рядок черги обробки видаляється як успішний, навіть якщо JSON не сформовано | `СМП_ОнлайнОбмен.ДанныеПоСсылкеВJSON_2`, `ВыгрузитьПоПравилу` |
| E3 | Немає ПКО з потрібним `ИмяПравила` у приймачі → об'єкт пропускається без помилки | `ПрочитатьОбъект` |
| E4 | У гілці `Исключение` `ПроизвестиЧтениеДанных` викликається `ФайлОбмена.Закрыть()`, а `ФайлОбмена` — `Соответствие` → другий виняток (його ковтає E1) | `ПроизвестиЧтениеДанных` |
| E5 | Протокол конвертації у фоновому завданні йде в `Сообщить` — видно лише в повідомленнях фонового завдання | `ЗаписатьВПротоколВыполнения` |
| E6 | Для старого шляху з масивом пакетів перевіряється код відповіді лише останнього POST | `ОтправитьСообщениеЧерезХТТП` |

## Мертвий / незавершений код

Поки що **не чіпаємо** — ревізія мертвого коду піде окремим issue **[автор]**. Список нижче —
вхідні дані для неї.

- `DataProcessors/СМП_JSONКонвертер` і `СМП_ОнлайнОбмен.ДанныеПоСсылкеВJSON` — попередній конвертер, не викликається.
- `СМП_ОнлайнОбменСобытия.ОтправитьСообщение` («СТАРАЯ ЛОГИКА УБРАТЬ!») і
  `СМП_ОнлайнОбменУправлениеОчередями.ОтправитьСообщение` — не викликаються.
- Статуси `Отправлено`, `ОшибкаДоставки`, `ОшибкаОтправки` — не встановлюються.
- HTTP `/metadata/` — заглушка.
- Транспорти `Ком`, `Файл` — заготовки **[автор]**.
- ТЧ `ОписаниеВыгружаемыхОбъектов` облікового запису — використовує лише `СМП_JSONКонвертер`.
- Константи/регістри у вивантаженні (`// to do: Доработать в будущем`), ПОД/ПВД, запити —
  не реалізовано. (`Алгоритмы.Параметры` — не незавершеність, а інформативний реквізит **[автор]**.)
- Закоментовані локальні шляхи розробника (`D:\_РобочіФайлиПрограмістів\...`).

## Відкриті питання до автора

1. ~~Автоповтор~~ — відповідь: ручний повтор свідомий (R3). Чи потрібне сповіщення про нові помилки в чергах?
2. Паралельність за користувачами — прийнятна чи були проблеми з порядком? (R6)
3. Чи траплялась ситуація R1 (довідник позначено вивантаженим, але не доставлено)?
4. ~~Розробка правил~~ — відповідь: у розширенні (зазвичай УНФ), далі XML КД2 → інші бази; сумісність з КД2 збережена.
5. ~~`Алгоритмы.Параметры`~~ — відповідь: інформативний реквізит (опис змінних контексту виклику).
6. ~~Мертвий код~~ — відповідь: не чіпати, окремий issue на ревізію.
7. ~~Болючі місця~~ — відповідь: виявляємо й описуємо по ходу робіт; цей файл — місце для них.
8. ~~Реальний JSON-пакет~~ — приклади в `samples/`, формат звірено (05).
