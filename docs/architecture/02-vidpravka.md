# 02. Відправка: від запису об'єкта до вихідної черги

## Точки входу — підписки на події

`EventSubscriptions/*.xml` → обробники в `CommonModules/СМП_ОнлайнОбменСобытия` **[код]**:

| Підписка | Подія | Обробник |
|---|---|---|
| `СМП_РегистрацияДокументаПередЗаписью` | `ПередЗаписью` документа | запам'ятовує `РежимЗаписи` у `ДополнительныеСвойства.СМП_РежимЗаписиДокумента` |
| `СМП_РегистрацияДокументаПриЗаписи` | `ПриЗаписи` документа | реєструє, якщо режим = `Запись` або `ОтменаПроведения` |
| `СМП_РегистрацияДокументаОбработкаПроведения` | `ОбработкаПроведения` | реєструє, якщо режим = `Проведение` |
| `СМП_РегистрацияСправочника` | `ПриЗаписи` довідника | реєструє, лише якщо елемент уже вивантажувався |

Тобто документ реєструється **один раз за запис**: при проведенні — з обробки проведення,
в інших режимах — з `ПриЗаписи`.

### Захист від «луни» і пропуски

- `ДополнительныеСвойства.СМП_ОтключитьРегистрациюВОчереди = Истина` → `ПередЗаписью` не
  ставить режим, отже нічого не реєструється. Приймач ставить цю властивість документам,
  які записує при завантаженні ([04](04-pryiom.md)).
- `ОбменДанными.Загрузка = Истина` або `Отказ` → `ПриЗаписи` нічого не робить. Довідники
  в приймачі завжди пишуться з `Загрузка = Истина`, тому зворотної реєстрації немає.
- **[гіпотеза]** `ОбработкаПроведения` не перевіряє `ОбменДанными.Загрузка`; від луни її
  захищає лише відсутність `СМП_РежимЗаписиДокумента`.

## Реєстрація документа

`СМП_ОнлайнОбменСобытия.ВыполнитьРегистрациюДокументаВОчереди` викликає
`СМП_ОнлайнОбменПравилаРегистрации.ПроверитьДокумент(Ссылка, ПолноеИмя, Дата)` **[код]**. Увесь
контур правил реєстрації — у цьому модулі (сервер + зовнішнє з'єднання):

1. `ПравилаДокумента(ПолноеИмя)` → `СМП_ОнлайнОбменПовтИсп.ПравилаРегистрацииДокумента(ПолноеИмя,
   ПолучитьФункциональнуюОпцию("СМП_ВерсияПравилРегистрации"))` — модуль з повторним
   використанням. **Ключ кешу — тип документа × версія правил**; версія — UUID у константі
   `СМП_ВерсияПравилРегистрации`, її міняють `ПриЗаписи` і `ПередУдалением` облікового запису
   (будь-який запис, також при `Загрузка`), тож кеш скидається в усіх сеансах.
2. Кеш наповнює `ПрочитатьПравилаДокумента` (привілейовано): один запит до ТЧ
   `Справочник.СМП_УчетныеЗаписиОбменов.ОбъектыКВыгрузке` за типом документа, лише непомічені
   облікові записи `НастройкаОбмена = ДляОтправки`, без `ПолучитьОбъект`. Правило —
   `ФиксированнаяСтруктура`: `УчетнаяЗапись`, `ДатаНачалаВыгрузкиДокументов`, `ТекстЗапроса`,
   `ПараметрыЗапроса`, `ТекстОшибки`. Текст перевіряється `Запрос.НайтиПараметры()`; порожній
   `ТекстЗапроса` (запис не перекомпільовано) дає `ТекстОшибки` «Правила регистрации не
   скомпилированы…».
3. Для кожного правила окремо: якщо `Объект.Дата < ДатаНачалаВыгрузкиДокументов` — правило не
   застосовується (ні запиту, ні помилки); інакше `ДокументыПроходящиеОтбор(Правило,
   [Ссылка])` — звичайний `Запрос` у привілейованому режимі з масивом `ПараметрСсылка`.
   Компоновка СКД при записі документа більше не виконується.
4. Документ пройшов → `СМП_ОнлайнОбменУправлениеОчередями.ДобавитьСообщениеВОчередьОбработки`.
   Правило невалідне або запит впав → `ДобавитьОшибкуРегистрацииВОчередьОбработки`: рядок
   `СМП_ОчередьОбработкиДанных` зі статусом `ОшибкаРегистрации` і текстом помилки, фонове завдання
   **не** запускається, запис документа не падає ([03](03-cherhy-i-transport.md)).

Текст запиту й параметри правила зберігаються в ТЧ `ОбъектыКВыгрузке` (`ТекстЗапроса`,
`ПараметрыЗапроса`) і готуються **при записі облікового запису** ([06](06-nalashtuvannya.md)):
СКД з відборами лишається джерелом для форми (`ОбъектыКВыгрузке.СКДДляОтборов`), але її текст
набору — `ВЫБРАТЬ РАЗРЕШЕННЫЕ * ИЗ Документ.<Имя> КАК ОБ ГДЕ ОБ.Ссылка В (&ПараметрСсылка)` — не
містить імен реквізитів.

Наслідки **[код]**:
- Фільтр `ДляОтправки` і позначка видалення тепер застосовуються: помічений на видалення запис
  і запис `ДляПолучения` у правилах не беруть участі.
- Кеш скидається версією правил при кожному записі чи видаленні облікового запису; перезапуск
  сеансів не потрібен.
- Перевірка відбору — один простий запит замість компоновки (≈6 мс проти ≈580 мс на документ
  на правило, виміри в базі агента **[перевірено]**); він виконується в транзакції запису
  документа й читає вже записані дані.
- Зламане правило (зникло поле відбору, запис не перекомпільовано після оновлення розширення)
  ніколи не розширює відбір мовчки: документ дає рядок `ОшибкаРегистрации`, а не піде в обмін,
  доки адміністратор не виправить правило й не виконає повторну перевірку.
## Реєстрація довідника

`СМП_СправочникПриЗаписиПриЗаписи` (привілейований режим) → `РС СМП_ВыгруженныеСправочники.
ПроверитьВыгрузкуЭлементаСправочника(Ссылка)` → для кожного облікового запису, яким елемент
уже вивантажувався, — `ДобавитьСообщениеВОчередьОбработки`.

Сам по собі довідник у обмін **не потрапляє** — лише разом з документом
([05](05-konvertatsiya.md#довідники-вже-вивантажені)). Повторний запис уже переданого
елемента викликає його повне повторне вивантаження **[автор][код]**.

## Черга обробки → вихідна черга

`ДобавитьСообщениеВОчередьОбработки` пише рядок у `СМП_ОчередьОбработкиДанных`
(`Статус = Новое`, `Данные = ЗначениеВСтрокуВнутр(Ссылка)`) і одразу викликає
`СформироватьОтправитьИсходящиеСообщенияВФоне` — фонове завдання
`СМП_ОнлайнОбмен.СформироватьОтправитьИсходящиеСообщения` з ключем
`<UUID облікового запису>/<UUID користувача ІБ>`; якщо активне завдання з таким ключем уже є,
нове не стартує.

Фонове завдання `СформироватьОтправитьИсходящиеСообщения`:

1. `Пауза(5)` — дає транзакції запису документа зафіксуватися.
2. Цикл, поки є рядки `Статус = Новое` цього користувача/обміну (порядок `ТаймШтамп`):
   - статус `ВОбработке`;
   - `ДанныеПоСсылкеВJSON_2` → масив JSON-рядків ([05](05-konvertatsiya.md));
   - кожен рядок → `ДобавитьСообщениеВОчередьИсходящих` (`Новое`);
   - рядок черги обробки видаляється (або `Обработано` у режимі налагодження);
   - `ВыполнитьОтправкуИсходящихСообщений` — одразу відправляє всі `Новое` вихідні цього
     користувача/обміну ([03](03-cherhy-i-transport.md));
   - виняток → `ОшибкаОбработки` + текст помилки.
3. Порожній результат — запис у ЖР «ОТЛАДКА! Завершено фоновое задание обмена» і вихід.

Регламентних завдань у розширенні немає: усе запускається подією запису **[код]**.
Повторна обробка помилкових рядків — вручну з форм списку черг (команда «Обработать сообщение»,
синхронно в сеансі користувача; для рядків `ОшибкаРегистрации` — спершу «Повторно проверить
правила регистрации», див. [03](03-cherhy-i-transport.md)). Це задумано: людина бачить помилку, виправляє причину і
повторює відправку **[автор]**.
