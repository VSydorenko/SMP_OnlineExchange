# 03. Черги, фонові завдання, статуси, транспорт

## Життєвий цикл повідомлення

```
Новое ──► ВОбработке ──► (успіх)  видалення          — звичайний режим
                    │             або Обработано/Доставлено — РежимОтладки
                    └──► (помилка) ОшибкаОбработки + СообщениеОбОшибке
```

- Статуси `Отправлено`, `ОшибкаДоставки`, `ОшибкаОтправки` оголошені, але жоден код їх не
  встановлює **[код]**; помилка HTTP-відправки теж пишеться як `ОшибкаОбработки`.
- Автоматичного повтору немає: обробники вибирають лише `Статус = Новое` **[код]**. Це
  **свідоме рішення**: помилку має побачити людина, виправити причину (правило, дані,
  налаштування) і повторити відправку вручну з форми списку черги **[автор]**.
- `ОбновитьСтатусСообщения` / `ЗаписатьОшибку` пишуть набори з `ОбменДанными.Загрузка = Истина`.

## Фонові завдання

| Завдання | Метод | Хто запускає | Ключ |
|---|---|---|---|
| «Обмен "<ім'я>": формирование и отправка исходящих сообщений» | `СМП_ОнлайнОбмен.СформироватьОтправитьИсходящиеСообщения` | `ДобавитьСообщениеВОчередьОбработки` (джерело) | `<UUID обліку>/<UUID користувача ІБ>` |
| «Обмен "<ім'я>": обработка входящих сообщений» | `СМП_ОнлайнОбмен.ОбработатьВходящиеСообщения` | `ДобавитьСообщениеВОчередьВходящих` (HTTP-сервіс, приймач) | те саме |

Для кожної пари «обліковий запис × користувач» працює щонайбільше одне завдання кожного виду.
Завдання ганяє цикл `Пока Истина`: перечитує чергу, доки є `Новое`, тому повідомлення, додані
під час роботи, підхоплює той самий запуск **[код]**.

Історія **[автор]**: раніше було одне фонове завдання, яке обробляло всі пакети однією чергою,
і тоді виникали проблеми з порядком об'єктів. Після переходу на окремі завдання за обліковим
записом і користувачем (версії сховища 77–78, 2026-07-07) проблем з порядком не спостерігається.
**[гіпотеза]** Причина — пов'язані об'єкти зазвичай створює той самий користувач (довідник,
потім документ), і тепер вони йдуть одним упорядкованим потоком, не перемішуючись з чужими.

Наслідки:
- Повідомлення різних користувачів обробляються **паралельними** завданнями; порядок між
  ними не гарантований — на практиці це не проблема **[автор]**.
- **[гіпотеза]** Вікно гонки: завдання вже отримало порожній результат і завершується, а
  інша транзакція саме фіксує новий рядок, для якого `ФоновыеЗадания.Выполнить` не стартував
  (бо завдання ще «Активно»). Такий рядок лишиться `Новое` до наступного запису цим
  користувачем.

## Відправка вихідних — `ВыполнитьОтправкуИсходящихСообщений`

- Вибірка `СМП_ОчередьИсходящихСообщений` за користувачем/обміном/статусом, `УПОРЯДОЧИТЬ ПО ТаймШтамп`.
- Для кожного рядка: `ВОбработке` → `СМП_ОнлайнОбменСобытия.ОтправитьИсходящееСообщение` →
  за `ВидТранспорта` викликає `СМП_СобытияОтправкиДанных.ОтправитьСообщениеЧерезХТТП`.
- Успіх (`201`) → видалення (або `Доставлено` у налагодженні); інакше `ОшибкаОбработки` з
  кодом і тілом відповіді.
- Невдала відправка **не зупиняє** обробку наступних рядків — документ може піти раніше за
  довідник, від якого він залежить **[код]**.

## HTTP-транспорт

Бази пари зазвичай розміщені на одному сервері; HTTP обрано як найпростіший і найзручніший
транспорт, а не для обміну через інтернет **[автор]**.

Клієнт — `СМП_СобытияОтправкиДанных.ОтправитьСообщениеЧерезХТТП`, бібліотека
`СМП_КоннекторHTTP`:

| Параметр | Значення |
|---|---|
| URL | `<ХттпСервисАдресПодключения>/hs/smp_exchange/data/<ИдентификаторОбмена>` |
| Метод | `POST` |
| Автентифікація | Basic, `ИмяПользователя:ПарольПользователя` з облікового запису |
| Тіло | JSON-рядок, стиснений **gzip** (`СМП_КоннекторHTTP.ЗаписатьGZip`); заголовок `content-type: application/json` |
| Таймаут | `0` (без обмеження) |
| Успіх | лише код `201` |

`Сессия`, `URI` і доп. параметри кешуються прямо в структурі налаштувань транспорту, яку
повертає `СМП_ОнлайнОбменПовтИсп.ПолучитьНастройкиТранспортаОбменаДанными` (кеш на сеанс).
Тож у межах сеансу (одного фонового завдання) HTTP-сесія перевикористовується; змінені
адреса/пароль підхоплюються лише новим сеансом **[код]**.

Перевірка зв'язку: `ПолучитьРезультатПроверкиПодключенияПоХТТП` → `GET .../ping/<Ид>`;
успіх = `200` з порожнім тілом. Викликається з форми облікового запису у фоні.

`ОтправитьСообщениеЧерезКОМ`, `ОтправитьСообщениеЧерезФайл` — заготовки, повертають
`Неопределено` **[автор][код]**. Якщо вибрати такий транспорт, `ВыполнитьОтправкуИсходящихСообщений`
впаде на `РезультатОтправки.Успешно` **[гіпотеза]**.

## HTTP-сервіс приймача — `HTTPServices/СМП_ОбменДанными`

Корінь `smp_exchange`, `ReuseSessions = AutoUse`, `SessionMaxAge = 20`.

| Шаблон | Метод | Обробник | Поведінка |
|---|---|---|---|
| `/data/{ИдентификаторОбмена}` | POST | `ОбменДаннымиDataPost` | Шукає обліковий запис `ДляПолучения` з цим ідентифікатором (404, якщо немає); розпаковує gzip; кладе рядок у `СМП_ОчередьВходящихСообщений`; стартує фонову обробку; відповідає **201** |
| `/ping/{ИдентификаторОбмена}` | GET | `ПроверкаСвязиPingGet` | 200 / 404 / 400 |
| `/validate/{ИдентификаторОбмена}` | POST | `СверкаValidatePost` | Звірка: стан і показники документів за списком GUID; 200 / 400 / 404 / 422 / 500, тіло — JSON. Див. [07](07-zvirka.md#контракт-validate) |
| `/metadata/` | GET | `ВыгрузкаОписанияМетаданныхMetadataGet` | Заглушка, завжди 200 |

**201 означає «прийнято в чергу», а не «завантажено»**. Результат завантаження в приймачі
джерело не бачить — зворотного каналу статусу немає **[код]**.

Користувач ІБ, під яким приходить HTTP-запит (Basic-автентифікація), стає
`ИдентификаторПользователяИБ` вхідних повідомлень і частиною ключа фонового завдання.
