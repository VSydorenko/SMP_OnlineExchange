# 05. Конвертація

Ядро — `DataProcessors/СМП_ОнлайнОбменКонвертацияОбъектов/Ext/ObjectModule.bsl` (11,2 тис.
рядків). Це модуль типової обробки КД2 `УниверсальныйОбменДаннымиXML`, адаптований під
JSON і правила з довідників. Велика частина оригінальної логіки лишилась закоментованою в
областях `СтараяЛогика` / `ОригинальнаяЛогика`; позначки адаптації — `// СМП ++ / --`,
`// SimplyUNF ++ / --` **[код]**.

Один і той самий клас обробки використовується в обох напрямах:

| Напрям | Вхід | Метод | Вихід |
|---|---|---|---|
| Вивантаження (джерело) | `мУчетнаяЗаписьОбмена`, `мСсылкаДляВыгрузки` | `ВыполнитьВыгрузку()` | `МассивСтрокJSON`, `мОшибки` |
| Завантаження (приймач) | `мУчетнаяЗаписьОбмена`, `мСтрокаJSON` | `ВыполнитьЗагрузку()` | записані об'єкти, `мОшибки` |

## Звідки беруться правила

`ЗагрузитьПравилаОбмена()` у кожному сеансі конвертації читає з бази **[код]**:

| Що | Джерело | Процедура |
|---|---|---|
| Структура «Конвертация» і глобальні обробники | реквізити облікового запису | `ЗаполнитьСтруктуруКонвертации` |
| ПКО | `Справочник.ПравилаКонвертацииОбъектов`, `Владелец = обліковий запис`, без груп, `ПО Порядок` | `ЗагрузитьПравилаКонвертации` / `ЗагрузитьПравилоКонвертации` |
| ПКС, ПКГС | `Справочник.ПравилаКонвертацииСвойств` (власник — ПКО; групи = ПКГС для ТЧ) | `ЗагрузитьСвойства`, `ЗагрузитьПКС`, `ЗагрузитьПКГС` |
| ПКЗ | `Справочник.ПравилаКонвертацииЗначений` | `ЗагрузитьЗначения` |
| Алгоритми | `Справочник.Алгоритмы` облікового запису → структура `Алгоритмы` (ключ — `Код`) | `ЗагрузитьАлгоритмы` |
| Запити, обробки, ПОД, ПВД | — | не реалізовано (закоментовано) |

Ім'я ПКО = `Код` елемента довідника. При вивантаженні ПКО прив'язується до типу за
`ТипИсточника`, при завантаженні — за `ТипПриемника`. **Тому і джерело, і приймач мають мати
власний набір правил під свій обліковий запис, а коди ПКО мають збігатися** (зв'язок — поле
`ИмяПравила` у JSON) **[код][автор]**.

Правила перечитуються з бази на кожне повідомлення (кешу між повідомленнями немає) **[код]**.

## Вивантаження: що потрапляє в пакет

`ОбработатьВыгружаемыеДанные` бере всі ПКО з `Источник = ТипЗнч(мСсылкаДляВыгрузки)` і для
кожного викликає `ВыгрузкаОбъектаВыборки` → `ВыгрузитьПоПравилу(…, ЭтоОсновнойОбъектВыгрузки = Истина)`.
Правил вивантаження даних (ПВД) немає: об'єкт визначено подією запису.

`ВыгрузитьПоПравилу` (рекурсивно для посилальних властивостей):
- обробники `ПередКонвертациейОбъекта` (глобальний), `ПередВыгрузкой`, `ПриВыгрузке`,
  `ПослеВыгрузки`, `ПослеВыгрузкиВФайл`;
- ПКЗ для перелічень/предвизначених;
- формує вузол `Ссылка` з полями пошуку і вузол `Свойства`;
- кожен **повністю** вивантажений об'єкт записується окремим елементом у `МассивСтрокJSON`
  (`ЗаписатьВФайл`). Вкладені об'єкти завершуються раніше за батьківський, тож у масиві
  залежні довідники йдуть **перед** документом.

`МассивСтрокJSON` → кожен рядок окремим повідомленням у вихідну чергу → окремим HTTP-запитом.

## Формат JSON-пакета

Звірено з реальними пакетами з [`samples/`](samples/) (правила «УНФ → BAS Бухгалтерія»):
[`01-dovidnyk-nomenclatura.json`](samples/01-dovidnyk-nomenclatura.json) — повне вивантаження
елемента довідника, [`02-dokument-nadhodzhennya.json`](samples/02-dokument-nadhodzhennya.json) —
документ. Одне повідомлення черги = один такий об'єкт.

### Об'єкт верхнього рівня

```json
{
  "Нпп": 1,
  "Тип": "ДокументСсылка.ПоступлениеТоваровУслуг",   // тип у ПРИЙМАЧІ (ПКО.Приемник)
  "ИмяПравила": "ПоступлениеТоваровУслуг",            // код ПКО — за ним приймач шукає правило
  "РежимЗаписи": "Проведение",                         // для документів
  "НеЗамещать": true,                                  // якщо задано в ПКО
  "Ссылка":   { "Нпп": 1, "Свойства": { /* поля пошуку */ } },
  "Свойства": { /* ПКС і табличні частини */ }
}
```

Інші можливі атрибути: `ГНпп`, `ПрефиксАвтонумерации`, `РежимПроведения`; у вузлі `Ссылка` —
`НеСоздаватьЕслиНеНайден`, `ПриПереносеОбъектаПоСсылкеУстанавливатьТолькоGIUD`.

### Вузол властивості

Ключ — ім'я реквізиту приймача (`ПКС.Приемник`) або ім'я параметра (`ПКС.ИмяПараметраДляПередачи`).
Значення — об'єкт (`ВыгрузитьСвойства`, `ObjectModule.bsl` ~9043–9105):

| Поле | Коли | Приклад |
|---|---|---|
| `ТипУзла` | `"Свойство"` — реквізит приймача; `"ЗначениеПараметра"` — параметр для обробників приймача, не реквізит | `"НалогообложениеНДС": {"ТипУзла": "ЗначениеПараметра", "Тип": "Строка", "Значение": "ОблагаетсяНДС"}` |
| `Значение` | примітивне значення; дати — ISO (`"2026-07-27T23:47:30"`, порожня — `"0001-01-01T00:00:00"`), перелічення — ім'я значення (`"НДС20"`) | `"Сумма": {"Значение": 2467.2}` |
| `Выражение` | ПКС з виразом — **рядок коду, який виконує приймач** | `"СтавкаНДС": {"ТипУзла": "Свойство", "Выражение": "Перечисления.СтавкиНДС.БезНДС"}` |
| `Ссылка` | посилальне значення: `Нпп` + `Свойства` з полями пошуку | див. нижче |
| `ИмяПКО` | якщо ПКО властивості відрізняється від типового для типу | `"ИмяПКО": "Контрагенты"` |
| `Тип` | тип приймача, якщо не виводиться з ПКО | `"Тип": "СправочникСсылка.КлассификаторУКТВЭД"` |
| `НеЗамещать` | ПКС з «Не замещать» | `"НеЗамещать": true` |

Порожні значення передаються вузлом без `Значение` (`"Комментарий": {"ТипУзла": "Свойство"}`).
Частина вузлів приходить без `ТипУзла` (`Код`, `ПометкаУдаления`, `Проведен`, `Сумма`) —
**[гіпотеза]** це властивості, записані скороченим шляхом (`ВыполнитьЗаписьСтруктурыВXML`);
приймач читає їх за ключем так само.

### Вузол посилання

```json
"Контрагент": {
  "ТипУзла": "Свойство",
  "ИмяПКО": "Контрагенты",
  "Ссылка": {
    "Нпп": 4,
    "Свойства": {
      "{УникальныйИдентификатор}": "00000000-0000-4000-8000-000000000004",   // якщо ПКО синхронізує за ідентифікатором
      "КодПоЕДРПОУ": { "Значение": "…" }           // поля пошуку ПКС
    }
  }
}
```

- `{УникальныйИдентификатор}` — рядок GUID джерела (без обгортки `{Значение}`).
- Поля пошуку можуть бути вкладеними посиланнями (договір → `Владелец` → контрагент).
- Пошук не обов'язково за GUID: у прикладі номенклатура шукається за параметром
  `ИдентификаторУТ` (`ТипУзла: ЗначениеПараметра`) — пошук виконує алгоритм ПКО приймача.
- Одне й те саме посилання в межах пакета має той самий `Нпп`.

### Табличні частини

```json
"ТабличнаяЧасть_Товары": { "Записи": [ { /* вузли властивостей рядка */ }, … ] }
```

Ключ — `ТабличнаяЧасть_<ім'я ПКГС>`; порожня ТЧ — `"Записи": []`. Приймач шукає ключ
`"ТабличнаяЧасть_" + ИмяСвойства` (`ObjectModule.bsl` ~4310) і читає масив `Записи` (~7478).

### Що видно з прикладів

- Документ несе довідники **лише вузлами посилань** (поля пошуку), без повних властивостей —
  повні дані довідника приходять окремим повідомленням, як у
  `01-dovidnyk-nomenclatura.json` **[код][приклад]**.
- Рядкові коди передаються з доповненням пробілами до довжини (`"ТВ-000001  "`).
- Приймач читає корінь як масив або як один об'єкт (`ПроизвестиЧтениеДанных`); фактично
  приходить один об'єкт на повідомлення.

## Довідники «вже вивантажені»

Механізм замість передачі повного довідника з кожним документом **[автор][код]**:

1. Під час вивантаження для **не основного** об'єкта з `ТипИсточника` `СправочникСсылка…` або
   `ПланВидовХарактеристикСсылка…` викликається `ЭтотОбъектУжеВыгружался(Источник)`:
   - є в `РС СМП_ВыгруженныеСправочники` для цього облікового запису → вивантажується лише
     вузол посилання (`ТолькоПолучитьУзелСсылки`) — поля пошуку без повних властивостей;
   - немає → вивантажується повністю і запам'ятовується в `СтекНеВыгружались`.
2. Наприкінці `ВыполнитьВыгрузку` усі `СтекНеВыгружались` записуються в
   `СМП_ВыгруженныеСправочники` (`ЗарегистрироватьВыгрузкуЭлементовСправочников`).
3. Повторний запис такого елемента довідника → підписка `СМП_РегистрацияСправочника`
   ставить його в чергу обробки як **основний** об'єкт → повне вивантаження.

Важливо: позначка ставиться на етапі **формування** JSON, до HTTP-доставки
(див. [90](90-ryzyky-i-pytannya.md)).

## Обробники й алгоритми

Тексти обробників зберігаються рядками в реквізитах (`Алгоритм…`) облікового запису, ПКО і ПКС
і виконуються через `Выполнить(...)` у контексті обробки конвертації — доступні її змінні
(`Источник`, `Приемник`, `Объект`, `Отказ`, `Алгоритмы`, `Правила`, `Конвертация` тощо), як у КД2.
Режим налагодження обробників КД2 (`ФлагРежимОтладкиОбработчиков`, зовнішня обробка) вимкнено.
Реквізит `Алгоритмы.Параметры` — **інформативний**: у ньому описують параметри/змінні з тіла
обробника, звідки викликається алгоритм. Алгоритм виконується в контексті обробника і бачить
його змінні напряму, тож нічого не передається **[автор]** (коментар `to do` у
`ЗагрузитьАлгоритм` застарілий).

## Завантаження і вивантаження правил у форматі КД2

**Як розробляють правила [автор]:** основне середовище розробки — саме розширення (форма
облікового запису, довідники ПКО/ПКС/ПКЗ, алгоритми, редактор коду). Формат правил повністю
сумісний з КД2, тож за потреби їх можна розробляти й у КД2. Зазвичай правила створюють на боці
**УНФ**, вивантажують у XML (`ВыгрузкаКонвертацииXML`) і завантажують в інші бази пари
(`ЗагрузкаКонвертацииXML`) — так коди ПКО в обох базах збігаються.

- `DataProcessors/ЗагрузкаКонвертацииXML` — читає XML правил КД2 (`ЧтениеXML`, підтримує
  `.zip`) і заповнює ПКО/ПКС/ПКЗ/алгоритми облікового запису (команда
  `ЗагрузитьПравилаКонвертации`).
- `DataProcessors/ВыгрузкаКонвертацииXML` — зворотний експорт у XML КД2, плюс вивантаження
  обробників у каталог.
- `DataProcessors/ЗагрузкаСтруктурыКонфигурации` — завантажує XML опису метаданих
  (як у КД2) у `Конфигурации/Объекты/Свойства/Значения`; викликається з форми облікового
  запису (`ЗагрузитьОписаниеКонфигурации`).
- `DataProcessors/АвтонастройкаПравилКонвертацииЗначений` — автозіставлення ПКЗ (форма
  облікового запису, «СинхронизацияЗначений»).
