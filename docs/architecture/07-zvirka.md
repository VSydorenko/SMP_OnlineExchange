# 07. Звірка «відправлено ↔ отримано»

Шляхи — відносно `СМП_ОнлайнОбменДанными/cfe/src/`. Уся логіка — у загальному модулі
`CommonModules/СМП_ОнлайнОбменСверка` (далі — «модуль»), рядки — його `Ext/Module.bsl`.

## Призначення

Звіт `СМП_СверкаДанныхОбмена` показує, чи кожен документ, що проходить ПРД облікового запису
за період, є в другій базі, в якому він стані і чи збігаються його ключові показники (суми,
ПДВ тощо). Вимоги й рішення — специфікації [фази 1](../specs/exchange-reconciliation.md) і
[фази 2](../specs/exchange-reconciliation-2.md). Лише документи, лише ПКО з пошуком за GUID,
звіт без дій над розбіжностями.

Звіт запускають **в обох базах**; режим визначає обліковий запис **[код]**:

| Режим | Запис | Еталон | Звірка «зайвого» |
|---|---|---|---|
| Джерело (фаза 1) | `ДляОтправки` | будує сама база | ні |
| Приймач (фаза 2) | `ДляПолучения` | будує **джерело** на запит приймача, по днях | так — регістр `СМП_ПолученныеОбъекты` |

**Принцип:** показники й допуск задає база, де запускають звірку: правила звірки цієї бази
визначають, які показники рахувати, і її допуск використовується в порівнянні. Друга база
лише рахує показники з тими самими кодами за своїми правилами.

### Режим джерела

```
Джерело                                            Приймач
Отчет.СМП_СверкаДанныхОбмена
 └─ ПолучитьДанныеСверки
     ├─ еталонний набір (період + ПРД)
     ├─ показники за правилами звірки ПКО джерела
     └─ POST gzip /validate/{Ид} {Версия 1} ─────────▶ СверкаValidatePost
         (порціями по N GUID)                         └─ ОбработатьЗапросValidate
                                                          └─ ОбработатьЗапросСверки
                                                              ├─ стан документів за GUID
     ◀──────────────── JSON 200 ──────────────────────        └─ показники за своїми правилами
 └─ ДобавитьСтрокиСверки, статуси → СКД → табличний документ
```

### Режим приймача

```
Приймач (звіт, запис ДляПолучения)                       Джерело
1. Тип документа → коди всіх ПКО запису з цим ТипПриемника
   + коди своїх показників кожного ПКО
2. По днях періоду:
   POST /validate/{Ид} {Версия 2, Запрос "Эталон"} ─────▶  запис ДляОтправки за Ид
                                                            на кожен ПКО: ЭталонныйНабор
                                                            (день, ДатаНачала, ПРД) + показники
   ◀──── GUID, ИмяПравила, стан, показники ───────────────  за своїми правилами того ПКО
3. Свої документи за GUID: стан, свої показники за ПКО з ИмяПравила,
   порівняння з допуском свого правила → статус
4. «Зайве»: документи типу за день, зареєстровані в СМП_ПолученныеОбъекты
   для цього запису, яких немає в еталоні дня
   POST /validate/{Ид} {Версия 2, Запрос "ПоискПоGUID"} ─▶  пошук GUID у ТипИсточника ПКО
   ◀──── Найден, стан, ПодлежитВыгрузке ──────────────────
5. Статус «зайвого» → таблиця «документ × показник» → СКД
```

## Правила звірки

`Справочник.СМП_ПравилаСверки`, власник — `ПравилаКонвертацииОбъектов` (ПКО), без ієрархії
**[код]**. Живуть **в обох базах**; кожна база рахує показник за власним правилом, по HTTP
передаються лише коди показників — код виразів мережею не йде.

| Поле | Зміст |
|---|---|
| `Код` | Рядок 50, унікальний у межах ПКО (`CodeSeries = WithinOwnerSubordination`), без автонумерації. Ключ показника в контракті `/validate` |
| `Наименование` | Рядок 100, заголовок показника у звіті |
| `Вид` | `Перечисление.СМП_ВидыПоказателейСверки`: `Реквизит` / `Выражение` |
| `Реквизит` | `СправочникСсылка.Свойства` — реквізит документа своєї бази |
| `Выражение` | Вираз для `Вычислить`, змінна контексту — `Объект` |
| `Допуск` | Допустима різниця для чисел; 0 — точний збіг. Береться з правила **бази, де запускають звірку** |
| `Информативный` | Лише виводиться у звіт, у розбіжність не потрапляє |
| `Порядок` | Порядок показників у звіті |
| `Отключить`, `Комментарий` | Вимкнути, не видаляючи; коментар |

**Вибір реквізиту.** Форма елемента відбирає `Свойства` за власником —
`СМП_ОнлайнОбменСверка.ОбъектСвоейБазы(ПКО)` (рядок 12): для запису `ДляОтправки` — `ПКО.Источник`,
для `ДляПолучения` — `ПКО.Приемник` — і за `Вид = СМП_ВидыСвойств.Реквизит`. Передумова — опис
метаданих обох конфігурацій завантажено (`ЗагрузкаСтруктурыКонфигурации`). Значення
показника — реквізит документа з ім'ям із найменування `Свойства`.

**Перевірки при записі** (`Catalogs/СМП_ПравилаСверки/Ext/ObjectModule.bsl`) **[код]**:

- `Код` і `Наименование` обов'язкові;
- `Вид = Реквизит` — обов'язковий `Реквизит`; посилальний тип у `Свойства.Типы` без
  `Информативный` — відмова (`СвойствоИмеетСсылочныйТип`, рядок 37);
- `Вид = Выражение` — обов'язковий `Выражение`.

Явних прав і команд у формах ПКО / облікового запису немає: у ролі `ПолныеПрава`
`setForNewObjects = true`, перехід до правил звірки — панель навігації ПКО.

## Обчислення показника

`ВычислитьПоказатели(Объект, Правила)` (рядок 110) — спільна для обох боків, повертає
`Соответствие` «код → `Структура("Значение")` | `Структура("Ошибка")`» **[код]**:

- `Реквизит` — `Объект[<ім'я реквізиту>]`;
- `Выражение` — `Вычислить` в окремій функції `ВычислитьВыражение` (рядок 244) після
  `УстановитьБезопасныйРежим(Истина)`. Вираз — одне значення, без операторів і циклів;
  процедури (`Записать()`) недоступні. Безпечний режим запис у базу не забороняє — захист
  від помилки автора правила, не від зловмисника. Привілейований режим у безпечному режимі
  **ігнорується**. Що не вміщується у вираз — експортна функція загального модуля, яку
  вираз викликає;
- неінформативний показник, що повернув посилання, — `Ошибка`;
- помилка одного показника не зупиняє решту;
- документ читається `Ссылка.ПолучитьОбъект()` (`ВычислитьПоказателиДокумента`, рядок 151);
  не прочитався — `Ошибка` на кожному показнику.

Для відповіді й для своєї сторони таблиці показники перекладаються у формат контракту
`ПоказателиДляОтвета` (рядок 520): на кожен запитаний код — `Значение`, `Ошибка` або
`НеНастроен` (правила з таким кодом немає).

**Нормалізація** (`НормализоватьЗначение`, рядок 215): число й булево — як є; рядок —
`СокрЛП`; дата — `XMLСтрока`; `Неопределено`/`Null` — `Неопределено` (JSON `null`); решта,
зокрема посилання, — `Строка(Значение)`.

**Порівняння** — у базі, де запускають звірку (`ЗначенияСовпадают`, рядок 191): різні типи —
розбіжність (порожнє не дорівнює нулю); число — `|джерело − приймач| ≤ Допуск`; рядок, дата,
булево — точно; `Информативный` не порівнюється.

## Контракт `/validate`

`POST /hs/smp_exchange/validate/{ИдентификаторОбмена}`, шаблон `Сверка` HTTP-сервісу
`СМП_ОбменДанными`, обробник `СверкаValidatePost` — див.
[03 · HTTP-сервіс приймача](03-cherhy-i-transport.md#http-сервіс-приймача--httpservicesсмп_обменданными).
Запит — JSON у gzip, відповідь — JSON без стиснення, `application/json; charset=utf-8`.

`СверкаValidatePost` спершу розпаковує тіло (збій — `400`), потім передає його диспетчеру
`ОбработатьЗапросValidate` (рядок 318); непередбачений виняток — `500` і запис у журнал
реєстрації (`ИмяСобытияЖурнала()`). Поле `Версия` — перемикач ролі бази **[код]**:

| `Версия` | Роль бази-сервера | Обліковий запис за Ид | Обробка |
|---|---|---|---|
| `1` (`ВерсияКонтракта()`) | приймач | `ДляПолучения` | `ОбработатьЗапросСверки` (рядок 372) |
| `2` (`ВерсияКонтрактаИсточника()`) | джерело | `ДляОтправки` | `ОбработатьЗапросИсточнику` (рядок 558), вид — поле `Запрос` |
| інша | — | — | `400` з `ПоддерживаемыеВерсии: [1, 2]` |

Помилки рівня запиту — JSON `{Версия, Ошибка}`: `404` — немає облікового запису потрібного
напряму; `400` — тіло не gzip/JSON, не та структура, невідома версія чи вид запиту; `422` —
немає ПКО з таким кодом, ПКО конвертує не документ, тип джерела ПКО відсутній в
`ОбъектыКВыгрузке` (версія 2), два правила запиту на один тип документа (версія 2); `500` —
непередбачена помилка. У відповідях версії 2 `Версия` = 2, крім помилок до визначення версії
(`400` на розпаковку чи розбір JSON, невідома версія) і `500` обробника — там `Версия` = 1.

### Версія 1: джерело питає приймач

Повний опис — [специфікація фази 1, розділ 3б](../specs/exchange-reconciliation.md#3б-контракт-validateидентификаторобмена).

- Запит: `Версия` = 1, `ИмяПравила` (код ПКО), `Показатели` (коди), `Объекты` (GUID). Один
  ПКО на запит.
- Відповідь `200`: на кожен GUID `Найден`, `Тип`, `Номер`, `Дата`, `Проведен`,
  `ПометкаУдаления`, `Показатели`; некоректний GUID — `Ошибка` на цьому об'єкті.
- Приймач: ПКО за кодом серед ПКО облікового запису, тип документа — з `ПКО.ТипПриемника`;
  правила звірки ПКО з кодами із запиту; стан — одним запитом за `Ссылка В (&Ссылки)`;
  показники — лише для знайдених **[код]**.

### Версія 2: приймач питає джерело

Повний опис — [специфікація фази 2, розділ 4](../specs/exchange-reconciliation-2.md#4-контракт-validateидентификаторобмена-версія-2).

- **«Эталон»** (`ОтветЭталон`, рядок 583): `Правила` — масив `{ИмяПравила, Показатели}` (коди
  показників **приймача**), `НачалоПериода`, `КонецПериода` (дата XML). Спершу перевіряються
  всі правила (`ПравилоИсточника`, рядок 789: ПКО, тип документа, правило реєстрації облікового
  запису; невалідне правило реєстрації — теж помилка) — будь-яка помилка дає `422` без даних. Потім на
  кожне правило — той самий `ЭталонныйНабор` (рядок 1154), що й у режимі джерела, і показники
  за правилами звірки ПКО джерела з кодами із запиту. Відповідь — на кожен документ
  `УникальныйИдентификатор`, `ИмяПравила`, `Тип`, `Номер`, `Дата`, `Проведен`,
  `ПометкаУдаления`, `Показатели`.
- **«ПоискПоGUID»** (`ОтветПоискПоGUID`, рядок 677): `Объекты` — масив
  `{УникальныйИдентификатор, ИмяПравила}`; джерело шукає GUID лише в типі джерела ПКО з
  `ИмяПравила`, стан — одним запитом на правило (`СостоянияДокументов`, рядок 879). Відповідь
  у порядку запиту: `Найден`; для знайдених ще `ИмяПравила`, `Тип`, `Номер`, `Дата`,
  `Проведен`, `ПометкаУдаления`, `ПодлежитВыгрузке` (`ВыгружаемыеДокументы`, рядок 841: `Дата ≥
  ДатаНачалаВыгрузкиДокументов` і документ проходить скомпільований запит правила реєстрації,
  порціями по 1000; та сама функція відбирає `ЭталонныйНабор`). Показників немає.
- Права — без привілейованого режиму, як і у версії 1.

Перевірка підключення з запису `ДляПолучения` — `GET /ping/{Ид}?side=source`: шукає
запис `ДляОтправки` (див. [03](03-cherhy-i-transport.md#http-сервіс-приймача--httpservicesсмп_обменданными)).

## Режим джерела: збір

`ПолучитьДанныеСверки(Параметры)` (рядок 995) **[код]**:

1. Перевірка параметрів (`ПроверитьПараметрыСверки`, рядок 1079): запис `ДляОтправки` або
   `ДляПолучения`, заповнені адреса підключення й `ИдентификаторОбмена`, тип — документ,
   коректний період. Помилки налаштування — виняток з текстом для користувача, до будь-якого
   HTTP-запиту. Запис `ДляПолучения` — далі режим приймача.
2. ПКО запису з `ТипИсточника = "ДокументСсылка.<Тип>"`, не помічений на видалення; немає
   або кілька — виняток «не поддерживается».
3. Еталонний набір: документи типу за період з `Дата ≥ ДатаНачалаВыгрузкиДокументов`, що
   проходять відбір правила реєстрації облікового запису: правило читає
   `СМП_ОнлайнОбменПравилаРегистрации.ПравилаУчетнойЗаписи` (без кешу), відбір застосовує
   `ДокументыПроходящиеОтбор` одним запитом на порцію з 1000 документів (той самий
   скомпільований запит, що й при записі документа). Невалідне правило (не скомпільоване,
   зникло поле) — виняток з текстом помилки, звірка зупиняється; помічені на видалення
   документи включаються. Порожній набір — порожній результат без HTTP-запитів.
4. Запити версії 1 порціями по `РазмерПорции` GUID (типово 50), тайм-аут — `Таймаут`
   (типово 60 с); адреса й Basic-авторизація — `СМП_ОнлайнОбмен.ПолучитьНастройкиТранспортаОбменаДанными`,
   відправка — `ОтправитьЗапросValidate` (рядок 1296). Помилка транспорту або відповідь не
   `200` — «Ошибка запроса» на всіх документах порції, решта порцій обробляється. Відповідь
   не-JSON з кодом `404` (вебсервер є, сервісу звірки за адресою немає — платформна сторінка
   HTML) — **зупинка звіту** (рішення автора 2026-10-26, симетрично до режиму приймача): «По
   адресу <ИнтернетАдрес> сервис сверки не найден (код 404): проверьте адрес подключения и
   публикацию базы-приемника; если они верны — обновите расширение в приемнике». Не-JSON з
   іншим кодом (`502`, `503` проксі тощо) — «Ошибка запроса» на документах порції з текстом
   «Приемник вернул ответ не в формате сверки (код N)», без твердження про розширення.
5. Рядки документа — спільна `ДобавитьСтрокиСверки` (рядок 1438); показники джерела — у
   форматі контракту (`ПоказателиДляОтвета`).

## Режим приймача: збір

`ДанныеСверкиПриемника(Параметры)` (рядок 1676) **[код]**:

1. ПКО запису з `ТипПриемника = "ДокументСсылка.<Тип>"`, не групи, не помічені на видалення
   (`ПКОДляТипаПриемника`, рядок 1735); немає — виняток. Параметр звіту — тип документа
   приймача, не ПКО: в один тип можуть конвертувати кілька ПКО, ПКО кожного документа
   визначає відповідь джерела. На кожен ПКО — свої правила звірки; у запит ідуть коди ПКО
   й коди їхніх показників.
2. Цикл по днях періоду (підперіод «Эталона» — 1 день, без параметра звіту): запит
   «Эталон» (`ВыполнитьЗапросКИсточнику`, рядок 1779).
3. Документи еталону (`ДобавитьСтрокиЭталона`, рядок 1859): свій документ —
   `Документы[Тип].ПолучитьСсылку(УИД)`, стан одним запитом на день; свої показники — за
   правилами ПКО з кодом `ИмяПравила`; порівняння з допуском свого правила. Некоректний GUID
   — «Нет в приемнике» з текстом помилки; `ИмяПравила`, якого не було в запиті, — «Ошибка
   запроса».
4. «Зайве» за той самий день (`ДобавитьСтрокиЛишних`, рядок 1947) — див. нижче.

**Помилки в режимі приймача** (`ВыполнитьЗапросКИсточнику`) **[код]**:

| Відповідь джерела | Реакція |
|---|---|
| `404` або `400` з `Версия ≠ 2` (джерело фази 1: його обробник шукає `ДляПолучения` ще до читання версії й дає `404` «В базе-приемнике…», або `400` з `ПоддерживаемыеВерсии: [1]`) | **зупинка звіту**: «…обновите расширение в источнике» |
| інші `404`, `400`; `422` на «Эталон» | **зупинка звіту**: «Источник отклонил запрос сверки (код N): …» — однакові для кожного дня |
| `404` не-JSON (вебсервер є, сервісу звірки за адресою немає — платформна сторінка HTML) | **зупинка звіту** (рішення автора 2026-10-26; раніше — однаковий рядок на кожен день): «По адресу <ИнтернетАдрес> сервис сверки не найден (код 404): проверьте адрес подключения и публикацию базы-источника; если они верны — обновите расширение в источнике» |
| `422` на «ПоискПоGUID» | «Ошибка запроса» на кандидатах порції: код ПКО береться з регістру, перейменований чи видалений у джерелі ПКО не зупиняє звіт назавжди |
| `500` (з будь-якою `Версия` — обробник `500` не знає версії запиту), інший не-`200`, транспорт, тайм-аут, не-JSON з кодом, відмінним від `404` (`502`, `503` проксі тощо — «Источник вернул ответ не в формате сверки (код N)», без твердження про розширення) | у «Эталоне» — один рядок «Ошибка запроса» на день (порожній документ, `ДатаИсточник` — день), «зайве» за день не перевіряється, наступні дні — далі; у «ПоискПоGUID» — «Ошибка запроса» на кандидатах порції |

## «Зайве» і регістр `СМП_ПолученныеОбъекты`

**Задача:** у режимі приймача показати документи, що прийшли цим обміном, але яких більше
немає в еталоні — видалені в джерелі або такі, що перестали проходити ПРД. Документи,
створені в приймачі вручну, не показуються.

**Ознака «прийшов з обміну»** — регістр відомостей `СМП_ПолученныеОбъекты` у приймачі
(неперіодичний, незалежний, керовані блокування) **[код]**:

| Поле | Вид | Тип |
|---|---|---|
| `УчетнаяЗаписьОбмена` | вимір, ведучий | `СправочникСсылка.СМП_УчетныеЗаписиОбменов` |
| `Объект` | вимір | рядок 150 — `ЗначениеВСтрокуВнутр(Ссылка)` |
| `ТипОбъекта` | реквізит | рядок 150 — `ПолноеИмя` метаданих |
| `ИмяПравила` | реквізит | рядок 50 — код ПКО |
| `ДатаПоследнегоПолучения` | реквізит | дата й час |

`Объект` — рядок, бо `ЛюбаяСсылка` не дозволяє режим сумісності розширення 8.3.17, а набори
типів посилань у вимірі регістру розширення недоступні. Модуль менеджера:
`ЗарегистрироватьПолучение` (рядок 10, запис за двома вимірами без попереднього читання) і
`ОтобратьПолученные` (рядок 38, таблиця посилань → тимчасова таблиця ⋈ регістр одним
пакетом).

**Коли пишеться.** У кінці `ПрочитатьОбъект` обробки `СМП_ОнлайнОбменКонвертацияОбъектов`
(див. [04](04-pryiom.md)): `ЗарегистрироватьПолучениеОбъекта` — лише документ із
непорожнім посиланням, за фактом отримання, навіть коли документ не перезаписувався.
Ранні виходи `ПрочитатьОбъект` (відмова обробника, `НеЗамещать` для знайденого документа)
не реєструють; «заглушки» (об'єкти, на які лише посилаються) — теж. Помилка запису регістру —
у протокол обміну без прапорця помилки, документ вантажиться далі. Очищення немає: запис
видаленого в приймачі документа нешкідливий — кандидати беруться з наявних документів.

**Кандидати дня** (`ДобавитьСтрокиЛишних`): документи типу за день, крім знайдених в еталоні,
→ `ОтобратьПолученные` → кандидати з `ИмяПравила`. Кандидати групуються за `ИмяПравила`;
запити «ПоискПоGUID» — порціями по `РазмерПорции` **у межах одного правила**
(`ДобавитьСтрокиПорцииЛишних`, рядок 2019), тож `422` на одне правило не зачіпає інших.

| Відповідь «ПоискПоGUID» | У звіті |
|---|---|
| `Найден: false` | Нет в источнике |
| знайдено, `ПодлежитВыгрузке` ≠ `true` | Не подлежит выгрузке (сторона джерела — з відповіді) |
| знайдено, `ПодлежитВыгрузке: true` | не показується (документ перезаписали поза періодом, повідомлення ще в черзі) |
| об'єкта немає у відповіді | Ошибка запроса, «Источник не вернул данные по документу.» |

Рядок «зайвого» — один на документ, без показників.

## Статуси і таблиця результату

Статус документа — перший, що підходить (`СтатусыСверки`, рядок 910; визначає
`ДобавитьСтрокиСверки`):

| Статус | Коли | Режим |
|---|---|---|
| Ошибка запроса | порція / день без коректної відповіді | обидва |
| Нет в приемнике | документа еталону немає в приймачі (або некоректний GUID); у фазі 1 — «Не найден» | обидва |
| Нет в источнике | «зайве»: джерело не знайшло GUID | приймач |
| Не подлежит выгрузке | «зайве»: у джерелі є, але не проходить ПРД або дата до `ДатаНачалаВыгрузкиДокументов` | приймач |
| Состояние отличается | різні `Проведен` або `ПометкаУдаления` | обидва |
| Расхождение показателей | хоч один неінформативний показник поза допуском | обидва |
| Показатель не проверен | `Ошибка` чи `НеНастроен` хоч на одному показнику («Источник: …», «Приемник: …») | обидва |
| Совпадает | решта | обидва |

Таблиця результату (`НоваяТаблицаСверки`, рядок 1322) — рядок «документ × показник»,
документ без показників — один рядок. Колонки **«Источник / Приемник» абсолютні** в обох
режимах: `НомерИсточник`, `ДатаИсточник`, `ПроведенИсточник`, … ліворуч — джерело, `…Приемник`
— приймач. `Документ` — посилання на документ **своєї** бази; у режимі приймача для «Нет в
приемнике» — порожнє, номер і дата — з джерела. `Правило` — код ПКО. `Найден` означає «є в
приймачі» в обох режимах.

## Звіт

`Reports/СМП_СверкаДанныхОбмена`, у підсистемі `СМП_ОнлайнОбменДанными` **[код]**:

- параметри — реквізити звіту: `УчетнаяЗапись` (записи обох напрямів), `ТипДокумента`
  (список вибору — `ТипыДокументовДляСверки`, рядок 935: для `ДляОтправки` — рядки
  `ОбъектыКВыгрузке`, для `ДляПолучения` — унікальні `ТипПриемника` ПКО запису, лише
  документи, за представленням), `НачалоПериода`/`КонецПериода` (типово минулий місяць),
  `РазмерПорции` (GUID на запит до приймача / на «ПоискПоGUID»), `Таймаут`, прапорець
  `ТолькоРасхождения` (ховає «Совпадает»); «зайве» шукається завжди;
- власна форма `ФормаОтчета` запам'ятовує обмін, тип документа, порцію, тайм-аут і
  «Только расхождения» між відкриттями (`AutoSaveDataInSettings`), період — ні;
- `ПриКомпоновкеРезультата` (модуль об'єкта звіту) — параметри → `ПолучитьДанныеСверки` →
  зовнішній набір `ДанныеСверки` основної СКД → табличний документ;
- СКД, два варіанти (рішення автора 2026-10-22):
  - **«Основной»** — зведення «Статус → кількість документів» (`Количество(Различные
    КлючДокумента)`: GUID документа рядком, для «Нет в приемнике» — GUID з відповіді джерела,
    для помилки дня — `Null`, тож дні не рахуються; `Документ` без свого документа теж `Null`, а
    не порожнє посилання, яке склеювало такі рядки в один документ), під ним крос-таблиця: рядки
    `Правило` → документ (`Документ`, `Статус`, `Отличия`; у групуванні ще `КлючДокумента`, не
    виводиться, — щоб два відсутні документи з однаковою датою не злипались), колонки — показники (за `Порядок`),
    у кожній «Источник | Приемник» (ресурси `Максимум` над рядковими значеннями). Клітинки
    крос-таблиці бере вибір групування рядків, а не вибір таблиці: ресурси вибрані в
    групуванні документа й не вибрані в групуванні `Правило`, тож рядок правила клітинок не
    має (прогін 2026-10-23: без ресурсів у виборі документа клітинки були порожні).
    Відбір колонок «Показатель заполнен» не виводиться. `Отличия` будує BSL (`ПоляВыводаДокумента`): лише те, що
    різниться («Проведен: Да → Нет; Номер: X → Y …»), плюс помилки документа й показників;
    для рядка помилки дня — з датою дня; збіг — порожньо. Рядок без свого документа, але з
    даними джерела («Нет в приемнике») починається з «В источнике: № X от дата» — інакше його
    в «Основном» не впізнати; у `СтатусОтличия` («Подробно») цього префікса немає, там
    документ джерела вже в колонці «Источник». Помилка такого рядка йде після префікса без
    дати дня (дата вже в «№ X от дата»); дата дня перед помилкою — лише в рядку помилки дня
    (немає ні документа, ні номера джерела). Статус: червоний — «Ошибка
    запроса», «Нет в приемнике/источнике», «Расхождение показателей»; помаранчевий —
    «Состояние отличается», «Не подлежит выгрузке», «Показатель не проверен»; сірий —
    «Совпадает». Клітинка показника з розбіжністю — рожевий фон (ресурс `ЕстьРасхождение`),
    інформативний показник — сірим. Кілька ПКО одного типу з різними показниками дають
    об'єднані колонки з порожніми клітинками — прийнятно;
  - **«Подробно»** — `Документ` → `Показатель` з однаковими колонками на обох рівнях:
    «Источник | Приемник | Статус / ошибка». Ресурси `Источник`, `Приемник`, `СтатусОшибка`
    мають окремі вирази для групувань `Документ` (номер і дата сторони — `ОписаниеИсточник`
    / `ОписаниеПриемник`; `СтатусОтличия`) і `Показатель` (значення; `ОшибкаПоказателя`).
    Розбіжне значення показника — рожевий фон і червоний текст (ресурс
    `РасхождениеПоказателя`, лише в групуванні `Показатель`, щоб не фарбувати рядок
    документа); рядок документа — жирним (ресурс `СтрокаДокумента`, лише в групуванні
    `Документ`); відбір вкладеного групування й загальні підсумки не виводяться;
  - сортування документів — за `ДатаИсточник` (рядки «Нет в источнике» з порожньою датою —
    першими); сирі поля (стан сторін, номери, дати, `Ошибка`) лишаються в схемі для
    «Изменить вариант»; розшифровка відкриває документ своєї бази. На формі звіту — «Изменить вариант» (структура, поля, відбори, оформлення),
  «Выбрать/Сохранить вариант»; `ПриКомпоновкеРезультата` бере настройки з
  `КомпоновщикНастроек` (порожня структура — `НастройкиПоУмолчанию` схеми).

Формування синхронне; фонове завдання — наступна ітерація.

## Обмеження

- Лише документи; ПКО з пошуком за полями (номер + дата), «1 → 2» — не підтримуються. Два ПКО
  на один тип джерела: у режимі джерела — виняток, у запиті «Эталон» — `422`.
- Документи, отримані до впровадження фази 2 (розширення 3.4.0.1) і з того часу не надіслані
  повторно, для «зайвого» невидимі — їх немає в `СМП_ПолученныеОбъекты`.
- «Зайве» — без показників: джерело показників не повертає, а свої без пари нічого не дають.
- Ранні виходи `ПрочитатьОбъект` з `НеЗамещать` (знайдений документ не перезаписується) не
  реєструють отримання.
- `СМП_ПолученныеОбъекты` не чиститься від записів видалених документів; довідники в нього
  не пишуться (структура дозволяє).
- Підперіод «Эталона» фіксований — 1 день.
- Повнота заповнення реквізитів, дії над розбіжностями, явні права й команди — наступні
  ітерації ([специфікація фази 1, розділ 8](../specs/exchange-reconciliation.md#8-поза-межами),
  [фази 2, розділ 10](../specs/exchange-reconciliation-2.md#10-поза-межами)).
- Розходження правил звірки між базами свідомо допускається; синхронізації немає.
- **Застереження: за наявності правил звірки перезавантажуйте правила КД2 режимом
  оновлення.** Режим заміни (`ЗагрузкаКонвертацииXML`) видаляє ПКО безпосередньо — разом з
  ними зникають і підпорядковані правила звірки.
