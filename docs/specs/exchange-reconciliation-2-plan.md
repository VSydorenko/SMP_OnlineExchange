# Звірка, фаза 2: запуск у приймачі — план реалізації

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** звіт `СМП_СверкаДанныхОбмена`, запущений з облікового запису `ДляПолучения`, бере еталон у джерела, порівнює його зі своїми документами за своїми правилами й показує «зайве» — документи, що прийшли обміном, але яких більше немає в еталоні.

**Architecture:** джерело стає сервером версії 2 контракту `/validate/{Ид}` (запити «Эталон» і «ПоискПоGUID») і будує еталон наявною `ЭталонныйНабор`. Приймач у новій `ДанныеСверкиПриемника` ходить до джерела по днях, сам рахує стан і показники та порівнює. Ознаку «прийшов з обміну» дає новий регістр `СМП_ПолученныеОбъекты`, який пише `ПрочитатьОбъект` при кожному завантаженні документа. Таблиця результату й рядки статусів стають симетричними: колонки «Источник / Приемник» абсолютні в обох режимах.

**Tech Stack:** 1С:Підприємство 8.3.27, режим сумісності розширення 8.3.17; Designer platform XML; Unica MCP (метадані, СКД, валідація, збірка, синтаксис); БСП (`ОбщегоНазначения`); `СМП_КоннекторHTTP` (HTTP, JSON, gzip).

**Spec:** [`docs/specs/exchange-reconciliation-2.md`](exchange-reconciliation-2.md) — читати разом із планом; механізм фази 1 — [`07-zvirka.md`](../architecture/07-zvirka.md).

## Global Constraints

- Платформа — 8.3.27.x; режим сумісності розширення — `Version8_3_17` (не підвищувати); методи новіші за 8.3.17 не використовувати.
- Формат вихідників — Designer platform XML під `СМП_ОнлайнОбменДанными/cfe/src`; модулі — UTF-8 з BOM, CRLF.
- Мова коду, синонімів і повідомлень — російська; тексти користувачу — `НСтр("ru = '...'")`.
- Версія розширення: `3.3.0.2` → `3.4.0.1`.
- Контракт `/validate/{Ид}`: версія `1` — без змін (сервер — приймач, запис `ДляПолучения`); версія `2` — сервер — джерело, запис `ДляОтправки`, поле `Запрос` = `"Эталон"` | `"ПоискПоGUID"`. Запит — JSON у gzip; відповідь — JSON без стиснення, `application/json; charset=utf-8`; помилки рівня запиту — `{Версия, Ошибка}`, коди `400`, `404`, `422`, `500`; невідома версія — `400` з `ПоддерживаемыеВерсии: [1, 2]`.
- Підперіод запиту «Эталон» — 1 день, без параметра звіту.
- Права — без привілейованого режиму; нових ролей не створювати (`ПолныеПрава`, `setForNewObjects = true`).
- Регістр `СМП_ПолученныеОбъекты`: неперіодичний, незалежний; виміри `УчетнаяЗаписьОбмена` (`СправочникСсылка.СМП_УчетныеЗаписиОбменов`, ведучий), `Объект` (рядок 150 — `ЗначениеВСтрокуВнутр(Ссылка)`); реквізити `ТипОбъекта` (рядок 150 — `ПолноеИмя`), `ИмяПравила` (рядок 50 — код ПКО), `ДатаПоследнегоПолучения` (дата й час).
- Статуси (порядок перевірки): Ошибка запроса → **Нет в приемнике** (колишнє «Не найден») → **Нет в источнике** → **Не подлежит выгрузке** → Состояние отличается → Расхождение показателей → Показатель не проверен → Совпадает.
- Автотестів немає. Перевірка — валідація Уніки, `operation=build`, `operation=syntax`, ручні КТ людини.

## Рішення плану (поверх специфікації)

Специфікація їх не фіксує; прийнято тут, людина бачить їх на рецензії плану.

- **П1. «Зайве» — без показників.** Рядок «Нет в источнике» / «Не подлежит выгрузке» — один на документ, без рядків показників: джерело показників не повертає, а свої без пари нічого не дають.
- **П2. Два правила запиту з одним `ТипИсточника`** у джерелі → `422` «несколько правил … не поддерживается», як у фазі 1 для двох ПКО на тип.
- **П3. Помилка запису регістру** — `ЗаписатьВПротоколВыполнения` з `ВзвестиФлагОшибок = Ложь` і `БезусловнаяЗаписьВПротоколОбмена = Истина`: прапорець помилки обміну не взводиться, повідомлення не стає помилковим.
- **П4. Ранні виходи `ПрочитатьОбъект`** з `НеЗамещать` (рядки 4109 і 4151 — знайдений документ не перезаписується) реєстрації не роблять: точка запису за специфікацією — лише кінець функції.
- **П5. Без нового значення «Найден» у джерелі:** колонка `Найден` таблиці означає «є в приймачі» в обох режимах.
- **П6. Рядки «Нет в источнике»** мають порожню `ДатаИсточник` і в СКД (сортування за `ДатаИсточник`) стоять першими.
- **П7. Список типів звіту** для обох режимів будує модуль (`ТипыДокументовДляСверки`), а не форма.

## Review Focus

1. **Джерело фази 1 на версію 2** відповідає JSON з `Версия` = 1: зазвичай `404` «В базе-приемнике не найдена учетная запись…» (обробник фази 1 шукає `ДляПолучения` до читання версії), або `400` з `ПоддерживаемыеВерсии: [1]`, якщо в джерелі є й запис `ДляПолучения` з цим Ид — звіт приймача має **зупинитися** з текстом «…обновите расширение в источнике», а не дати рядок помилки на кожен день. Перевірка — КТ3, сценарій 3 (Task 5).
2. **Джерело без `/validate` взагалі** (платформний `404` з HTML) — не фатально: рядок «Ошибка запроса» на день із текстом «…обновите расширение в источнике». Перевірка — КТ3, сценарій 4.
3. **Регресія режиму джерела** після переходу на симетричну `ДобавитьСтрокиСверки`: тексти помилок показників, статуси й значення — як у фазі 1, змінилася лише назва «Нет в приемнике». Перевірка — КТ4 (Task 4).
4. **Документ, видалений у приймачі, із записом у регістрі** — у кандидати не потрапляє (кандидати беруться з наявних документів), звіт не падає. Перевірка — КТ3, сценарій 9.
5. **Битий GUID у відповіді «Эталон»** — рядок «Нет в приемнике» з текстом помилки, а не виняток на весь день. Перевірка — читанням коду на рецензії Task 5 (на петлі не відтворюється).
