# Звірка, фаза 2: запуск у приймачі — специфікація

> Стан: чернетка на рецензії. Гілка — `feature/exchange-reconciliation-2`.
> Продовжує [фазу 1](exchange-reconciliation.md); механізм фази 1 — [07 · Звірка](../architecture/07-zvirka.md).
> Позначки як у фазі 1: **[код]**, **[автор]**, **[рішення]**, **[?]**.
> Шляхи — відносно `СМП_ОнлайнОбменДанными/cfe/src/`.

## 1. Початковий опис

Зараз звірка працює на боці джерела, орієнтуючись на типи документів, які вивантажуються.
Треба зробити механізм запуску звірки на боці приймача. В обліковому записі приймача списку
типів документів немає, є лише ПКО — орієнтуватися треба на них **[автор]**.

## 2. Що змінюється

| | Фаза 1 | Фаза 2 |
|---|---|---|
| Де запускають звірку | лише в джерелі (`ДляОтправки`) | ще й у приймачі (`ДляПолучения`) |
| Звіт | `СМП_СверкаДанныхОбмена` | той самий; режим визначає обліковий запис **[рішення]** |
| Еталонний набір | будує джерело | будує **джерело** в обох режимах — у режимі приймача на запит приймача **[рішення]** |
| Контракт `/validate/{Ид}` | версія 1: джерело питає приймач | + версія 2: приймач питає джерело; версія 1 без змін |
| Нове | — | «зайве в приймачі»; регістр `СМП_ПолученныеОбъекты`; статуси «Нет в источнике», «Не подлежит выгрузке» |

**Принцип [рішення]:** показники й допуск задає база, де запускають звірку. Для режиму джерела
це вже так; у фазі 1 це було сформульовано як «допуск з правила джерела».

## 3. Режим приймача: потік

```
Приймач (звіт, запис ДляПолучения)                       Джерело
1. Тип документа → коди всіх ПКО запису з цим ТипПриемника
   + коди своїх показників кожного ПКО
2. По днях періоду:
   POST /validate/{Ид} {Версия 2, Запрос "Эталон"} ─────▶  запис ДляОтправки за Ид
                                                            на кожен ПКО: ЭталонныйНабор
                                                            (день, ДатаНачала, ПРД) + показники
   ◀──── GUID, ИмяПравила, стан, показники ───────────────  за своїми правилами того ПКО
3. Свої документи за GUID: стан, свої показники за ПКО з ИмяПравила,
   порівняння з допуском свого правила → статус
4. «Зайве»: документи типу за день, зареєстровані в СМП_ПолученныеОбъекты
   для цього запису, яких немає в еталоні дня
   POST /validate/{Ид} {Версия 2, Запрос "ПоискПоGUID"} ─▶  пошук GUID у ТипИсточника ПКО
   ◀──── Найден, стан, ПодлежитВыгрузке ──────────────────
5. Статус «зайвого» → таблиця «документ × показник» → СКД
```

- **Параметр звіту — тип документа приймача [рішення]**, не ПКО: в один тип приймача можуть
  конвертувати кілька ПКО, і за одним ПКО документи інших потрапили б у «Нет в источнике».
  ПКО кожного документа визначає відповідь джерела.
- **Еталон будує джерело [рішення]** тим самим кодом, що й у своєму звіті: документи, створені
  в приймачі вручну, в еталон не потрапляють за побудовою — шуму немає. Розглянуто й відкинуто:
  еталон «усі документи типу в приймачі» (шум від локальних документів).
- **Підперіод запиту «Эталон» — 1 день [рішення]**, без параметра у звіті: перевірка ПРД у
  джерелі йде по одному документу, день вкладається в тайм-аут.

## 4. Контракт `/validate/{ИдентификаторОбмена}`, версія 2

Той самий ресурс і обробник `СверкаValidatePost` **[рішення]**; запит — JSON у gzip, відповідь —
JSON без стиснення, як у версії 1. Версія — перемикач ролі: `1` — сервер є приймачем (шукає
`ДляПолучения`), `2` — сервер є джерелом (шукає `ДляОтправки`). Поле `Запрос` вибирає вид.
Відкинуто: окремі ресурси (старе джерело відповідало б платформним 404 з HTML, ще два шаблони
URL); версія 1 без явної ролі (неоднозначно, коли в базі обидва записи з одним Ид).

### «Эталон»

```json
{ "Версия": 2, "Запрос": "Эталон",
  "Правила": [ { "ИмяПравила": "РеализацияТоваров", "Показатели": ["Сумма", "СуммаНДС"] },
               { "ИмяПравила": "ВозвратТоваров",    "Показатели": ["Сумма"] } ],
  "НачалоПериода": "2026-09-03T00:00:00", "КонецПериода": "2026-09-03T23:59:59" }
```

`Показатели` — коди показників **приймача** для цього ПКО. Відповідь `200`:

```json
{ "Версия": 2, "Объекты": [
  { "УникальныйИдентификатор": "9f1c…", "ИмяПравила": "РеализацияТоваров",
    "Тип": "Документ.РеализацияТоваровУслуг", "Номер": "УТ-000123", "Дата": "2026-09-03T10:20:00",
    "Проведен": true, "ПометкаУдаления": false,
    "Показатели": { "Сумма": { "Значение": 1200.00 }, "СуммаНДС": { "НеНастроен": true } } } ] }
```

Значення показників — як у версії 1: `Значение` / `Ошибка` / `НеНастроен`, нормалізація —
`НормализоватьЗначение`.

### «ПоискПоGUID»

```json
{ "Версия": 2, "Запрос": "ПоискПоGUID",
  "Объекты": [ { "УникальныйИдентификатор": "a27b…", "ИмяПравила": "РеализацияТоваров" } ] }
```

`ИмяПравила` на кожному GUID — з регістру `СМП_ПолученныеОбъекты` (розділ 7): джерело шукає
лише в типі цього ПКО. Відповідь `200` — на кожен GUID `Найден`; знайдений — ще `ИмяПравила`,
`Тип`, `Номер`, `Дата`, `Проведен`, `ПометкаУдаления`, `ПодлежитВыгрузке`. Показників немає.

`ПодлежитВыгрузке` = `Дата ≥ ДатаНачалаВыгрузкиДокументов` **і** документ проходить ПРД
(`СМП_ОнлайнОбменСобытия.ПроверитьОбъектПоУсловиямОтбора`).

### Помилки рівня запиту

Тіло — JSON `{Версия, Ошибка}`, як у версії 1:

| Код | Коли |
|---|---|
| `404` | немає облікового запису (`ДляОтправки` для версії 2) з цим Ид |
| `422` | невідомий код ПКО; ПКО конвертує не документ; тип джерела ПКО відсутній в `ОбъектыКВыгрузке` |
| `400` | тіло не gzip/JSON; невідомий `Запрос`; невідома версія — з `ПоддерживаемыеВерсии: [1, 2]` |
| `500` | непередбачена помилка; запис у журнал реєстрації (`ИмяСобытияЖурнала()`) |

Старе джерело (фаза 1) на `"Версия": 2` відповідає JSON з `Версия` = 1: `404` «нет учетной записи
`ДляПолучения`» (обробник фази 1 шукає запис до читання версії) або `400` з
`ПоддерживаемыеВерсии: [1]`. Приймач будь-яку не-`200` JSON-відповідь з `Версия ≠ 2` вважає старим
джерелом.

## 5. Джерело

- **Вхід [рішення]:** `СверкаValidatePost` спершу розпаковує тіло й читає `Версия`: `1` →
  запис `ДляПолучения` і наявна `ОбработатьЗапросСверки`; `2` → запис `ДляОтправки`
  (`ПолучитьУчетнуюЗаписьОбменаПоИд(Ид, Ложь)`) і нова `ОбработатьЗапросИсточнику`, що
  розгалужується за `Запрос`.
- **«Эталон»:** на кожне правило — `НайтиПКОПоКоду`; документи — наявна
  `ЭталонныйНабор(Параметры, МетаданныеДокумента)` для `ПКО.ТипИсточника` (період,
  `ДатаНачалаВыгрузкиДокументов`, ПРД з рядка `ОбъектыКВыгрузке`, помічені на видалення
  включаються), сигнатуру не змінювати; показники — `ПравилаСверки(ПКО, КодыПоказателей)` і
  `ПоказателиДляОтвета`.
- **«ПоискПоGUID»:** посилання `Документы[ТипИсточника].ПолучитьСсылку(УИД)`, стан — один
  запит `Ссылка В (&Ссылки)` на тип; `ПодлежитВыгрузке` рахується лише для знайдених.
- **Права [рішення]:** без привілейованого режиму — як відповідь приймача у фазі 1.
- **Перевірка підключення [рішення]:** `/ping/{Ид}` приймає необов'язковий параметр
  `?Сторона=Источник` — тоді шукає `ДляОтправки`. Без параметра — як зараз.

## 6. Приймач і звіт

### Потік

`ПолучитьДанныеСверки` розгалужується за `НастройкаОбмена` запису: `ДляОтправки` — без змін,
`ДляПолучения` — нова `ДанныеСверкиПриемника` **[рішення]**:

1. ПКО запису з `ТипПриемника` = обраний тип (не помічені на видалення); немає — виняток.
2. По днях: «Эталон» → свої документи `Документы[Тип].ПолучитьСсылку(УИД)`, стан одним
   запитом; свої показники — `ВычислитьПоказателиДокумента` за `ПравилаСверки` свого ПКО з
   кодом `ИмяПравила`; порівняння — `ЗначенияСовпадают` з допуском **свого** правила.
3. «Зайве» за той самий день (розділ 7) — «ПоискПоGUID» порціями по `РазмерПорции`.

### Статуси

Статус документа — перший, що підходить:

| Статус | Коли | Режим |
|---|---|---|
| Ошибка запроса | порція / день без коректної відповіді | обидва |
| **Нет в приемнике** | документа еталону немає в приймачі (раніше — «Не найден») **[рішення]** | обидва |
| **Нет в источнике** | «зайве»: джерело не знайшло GUID | приймач |
| **Не подлежит выгрузке** | «зайве»: у джерелі є, але не проходить ПРД або дата до `ДатаНачалаВыгрузкиДокументов` | приймач |
| Состояние отличается | різні `Проведен` / `ПометкаУдаления` | обидва |
| Расхождение показателей | неінформативний показник поза допуском | обидва |
| Показатель не проверен | `Ошибка` / `НеНастроен` хоч на одному показнику | обидва |
| Совпадает | решта | обидва |

«Зайве», яке джерело знайшло й яке **підлягає** вивантаженню (дата поза обраним періодом —
документ перезаписали, повідомлення ще в черзі), **не показується [рішення]**.

### Таблиця результату й СКД

- **Колонки «Источник / Приемник» абсолютні [рішення]**: в обох режимах ліворуч — джерело,
  праворуч — приймач. `Документ` — посилання на документ **своєї** бази (розшифровка відкриває
  його); у режимі приймача для «Нет в приемнике» — порожнє, номер і дата — з джерела.
- `Номер` / `Дата` перейменувати на `НомерИсточник` / `ДатаИсточник` (у фазі 1 вони вже
  означали джерело) — разом із полями СКД.
- Нова колонка **`Правило`** — код ПКО.
- Помилка «Эталона» за день — **один рядок на день**: порожній документ, `ДатаИсточник` — день,
  статус «Ошибка запроса», текст помилки; «зайве» за цей день не перевіряється **[рішення]**.

### Форма звіту

- `УчетнаяЗапись` — записи обох напрямів.
- Список `ТипДокумента`: `ДляОтправки` — з `ОбъектыКВыгрузке`; `ДляПолучения` — унікальні
  `ТипПриемника` ПКО запису, лише документи.
- `РазмерПорции`: у режимі джерела — GUID на запит до приймача; у режимі приймача — GUID на
  «ПоискПоGUID». `Таймаут` — в обох.
- Перевірки до запитів: заповнені адреса підключення й `ИдентификаторОбмена`.
- «Зайве» шукається завжди, без прапорця **[рішення]**.

### Обліковий запис

Кнопку «Проверить подключение» відкрити для `ДляПолучения`; перевірка — `/ping/{Ид}?Сторона=Источник`.
Адреса й облікові дані джерела — наявні поля `ХттпСервисАдресПодключения`, `ИмяПользователя`,
`ПарольПользователя` (форма вже показує їх для способу «ХттпСервис»).

## 7. «Зайве в приймачі» і регістр `СМП_ПолученныеОбъекты`

**Задача:** показати документи, що прийшли цим обміном, але яких більше немає в еталоні —
видалені в джерелі або такі, що перестали проходити ПРД. Документи, створені в приймачі
вручну, показувати не можна.

**Ознака «прийшов з обміну» — регістр у приймачі [рішення]:**

| Поле | Вид | Тип |
|---|---|---|
| `УчетнаяЗаписьОбмена` | вимір, ведучий | `СправочникСсылка.СМП_УчетныеЗаписиОбменов` |
| `Объект` | вимір | рядок 150 — `ЗначениеВСтрокуВнутр(Ссылка)`, як `ЭлементСправочника` у `СМП_ВыгруженныеСправочники` |
| `ТипОбъекта` | реквізит | рядок — `ПолноеИмя` метаданих |
| `ИмяПравила` | реквізит | рядок — код ПКО |
| `ДатаПоследнегоПолучения` | реквізит | дата й час |

Неперіодичний; назва — під майбутні довідники. Модуль менеджера — реєстрація отримання
(запис за двома вимірами без попереднього читання) і перевірка, за зразком
`СМП_ВыгруженныеСправочники`.

- **Тип виміру `Объект`:** `ЛюбаяСсылка` не дозволяє режим сумісності розширення (8.3.17);
  набори типів `ДокументСсылка` / `СправочникСсылка` у вимірі регістру розширення недоступні —
  лише конкретні запозичені типи **[автор, перевірено]**. Тому рядок; конвертація посилання в
  рядок — у коді (мова запитів її не вміє).
- **Коли пишеться [рішення]:** явним викликом у кінці `ПрочитатьОбъект` обробки
  `СМП_ОнлайнОбменКонвертацияОбъектов`, перед `Возврат Объект` — туди сходяться обидві гілки
  запису документа. Умова: об'єкт отримано повністю, `ИмяТипаОбъекта = "Документ"`, посилання
  не порожнє. Реєструється **за фактом отримання, навіть коли документ не записувався**
  (`ЗаписыватьВИнформационнуюБазуТолькоИзмененныеОбъекты`, `НужноЗаписатьОбъект = Ложь`):
  старі документи, надіслані повторно, самі потрапляють у регістр.
- **Не реєструються:** «заглушки» (`СоздатьНовыйОбъект` з `ЗаписыватьОбъектСразуПослеСоздания`,
  відкладений запис `ПровестиЗаписьНеЗаписанныхОбъектов`).
- **Помилка запису регістру:** у протокол обміну, документ вантажиться далі; наступне
  отримання виправить. Відкинуто: підписка `ПриЗаписи` з `ДополнительныеСвойства` — не бачить
  отриманих без змін документів, а помилка регістру скасовувала б запис документа.
- **Видалення:** без підписки на видалення й без очищення **[рішення]**. Запис видаленого в
  приймачі документа лишається нешкідливим — кандидати беруться з наявних документів.
- **Вибір кандидатів за день:** запит документів типу → `ЗначениеВСтрокуВнутр` у циклі →
  таблиця-параметр → тимчасова таблиця ⋈ регістр за `УчетнаяЗаписьОбмена` і `Объект` — одним
  пакетом; мінус GUID еталону дня.

| Відповідь «ПоискПоGUID» | У звіті |
|---|---|
| `Найден: false` | Нет в источнике |
| знайдено, `ПодлежитВыгрузке: false` | Не подлежит выгрузке |
| знайдено, `ПодлежитВыгрузке: true` | не показується |

**Обмеження [рішення]:** документи, отримані до впровадження фази 2 і з того часу не надіслані
повторно, для «зайвого» невидимі.

Розглянуто й відкинуто як ознаку «з обміну»:

| Варіант | Чому ні |
|---|---|
| Коментар першої версії БСП (`ВерсииОбъектов`) | залежить від налаштувань версіонування; у режимі обміну БСП не пише версію нового документа — потрібне втручання в регістр БСП; коментар лише з v79 |
| Автор першої версії | автор — не точна ознака; людина відмовилась від страховки |
| Спільний реквізит | розширення не може додати спільний реквізит |
| Розділювачі (`ОбластьДанных…`) | номер області даних — у хмарі документ опинився б в області іншого абонента |
| Регістр відправлених у джерелі | приймачу довелося б слати GUID **усіх** документів типу, включно з локальними |
| Реквізит у запозичених документах | запозичувати кожен тип у кожній конфігурації клієнта |
| Поля документа (`Комментарий`, `Автор`) | видимі й змінювані користувачем, залежать від конфігурації |
| Платформна `ИсторияДанных`, черга вхідних | вмикається в метаданих конфігурації / черга чиститься |

## 8. Помилки в режимі приймача

| Що | Реакція |
|---|---|
| Запис без адреси / Ид; тип без ПКО | виняток з текстом до будь-якого запиту |
| `404`, `422`, `400` з `ПоддерживаемыеВерсии` від джерела | **зупинка всього звіту** з текстом (однакові для кожного дня); старе джерело — «…обновите расширение в источнике» |
| Транспорт, тайм-аут, `500`, не-JSON у «Эталоне» | рядок «Ошибка запроса» за день; наступні дні — далі |
| Те саме в «ПоискПоGUID» | «Ошибка запроса» на кандидатах порції |
| Помилка запису `СМП_ПолученныеОбъекты` при завантаженні | протокол обміну; документ вантажиться |

## 9. Перевірка

Автотестів у репозиторії немає — ручні контрольні точки з галками в плані; плюс синтаксис і
збірка `.cfe` Унікою.

- **На петлі (база агента).** Запис `ДляПолучения` звертається до самої бази як до джерела —
  версія 2 шукає запис за роллю.
  1. Еталон: «Совпадает»; «Расхождение показателей» з допуском приймача; «Показатель не
     проверен» (у джерелі немає правила для коду); «Нет в приемнике»; кілька ПКО на тип —
     колонка `Правило`.
  2. Помилки: хибний хост — рядки за дні; неіснуючий Ид — зупинка з текстом; база фази 1 —
     «обновите расширение в источнике».
  3. «Зайве» — записи регістру вносяться вручну: GUID, якого немає в джерелі → «Нет в
     источнике»; документ, що не проходить ПРД → «Не подлежит выгрузке»; документ, що
     проходить, поза періодом → рядка немає; документ без запису → рядка немає.
  4. Регресія режиму джерела: ті самі результати, змінилася лише назва «Нет в приемнике».
- **На реальній парі (людина).** Реєстрація при завантаженні: новий документ; повторно
  надісланий без змін; заглушка не реєструється.

## 10. Поза межами

- Очищення `СМП_ПолученныеОбъекты` від записів видалених документів.
- Реєстрація довідників у `СМП_ПолученныеОбъекты` (структура вже дозволяє).
- Параметр звіту «днів у запиті».
- Решта пунктів розділу 8 фази 1: ПКО з пошуком за полями, «1 → 2», повнота заповнення, дії
  над розбіжностями, явні права й команди, збереження правил звірки при заміні правил КД2,
  синхронізація правил між базами, фонове формування.
