# Звірка «відправлено ↔ отримано» — план реалізації (ітерація 1)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** звіт `СМП_СверкаДанныхОбмена` у базі-джерелі показує, чи кожен документ, що проходить ПРД обліковим записом за період, є в приймачі, в якому стані, і чи збігаються його показники.

**Architecture:** правила звірки (`Справочник.СМП_ПравилаСверки`, підпорядкований ПКО) живуть в обох базах. Уся логіка — у загальному модулі `СМП_ОнлайнОбменСверка`: обчислення показників, обробка запиту в приймачі (новий ресурс `POST /validate/{ИдентификаторОбмена}` HTTP-сервісу `СМП_ОбменДанными`), збір даних і порівняння в джерелі. Звіт лише викликає модуль і виводить готову таблицю через СКД із зовнішнім набором.

**Tech Stack:** 1С:Підприємство 8.3.27, режим сумісності розширення 8.3.17; Designer platform XML; Unica MCP (метадані, форми, СКД, збірка, синтаксис); БСП (`ОбщегоНазначения`); `СМП_КоннекторHTTP` (HTTP, JSON, gzip).

**Spec:** [`docs/specs/exchange-reconciliation.md`](exchange-reconciliation.md) — читати разом із планом.

## Правила виконання

План виконує окрема сесія-виконавець (простіша модель) скілом `superpowers:executing-plans`.
Архітектор, рецензент і той, хто приймає рішення по ходу виконання, — сесія `exchange-main`.
Людина тестує розширення після реалізації (КТ1–КТ3) і лишає за собою межі з пункту 5.

1. **Одна сесія за раз.** Робоча копія й база агента `unf_test_claude` спільні: поки працює
   виконавець, `exchange-main` не змінює файли й не збирає базу.

   (помилка валідації, синтаксису чи збірки; Unica відмовляє або робить не те; код плану не
   компілюється; немає очікуваного файлу чи тега) — **зупинитися**, нічого не обходити й не
   переписувати на свій розсуд. Надіслати `exchange-main` (SendMessage, `to: "exchange-main"`):
   завдання і крок, точна команда, повний вивід помилки, що вже змінено й не закомічено.
   Чекати відповіді й виконати рішення `exchange-main` дослівно; у коміті, що його
   застосовує, — рядок `Відступ від плану: <коротко>, рішення exchange-main`.
3. **Не змінювати план і специфікацію.** Правки в них вносить лише `exchange-main` (коли
   виконавець стоїть). Знайдена хиба плану — це доповідь за пунктом 2.
4. **Зупинки на рецензію.** Після Task 2, Task 5 і Task 6 — стоп і повідомлення
   `exchange-main` «Task N готово, коміти <хеші>». Наступне завдання — лише після «далі» від
   `exchange-main`. Перед Task 8 — рецензія всієї гілки. Ручні КТ1–КТ3 людина проходить
   після реалізації — виконавець їх не чекає (кроки КТ — пропускати з позначкою «КТ — людина,
   після реалізації»).
5. **Межі репозиторію** (`CLAUDE.md`): сховище — тільки читання; пише лише в базу агента;
   `-Apply` і `git push` / PR — лише на явне прохання людини; підрядки `лиценз`, `ліценз`,

6. **Коміти** — лише свої зміни поточного завдання, повідомлення з плану.

## Global Constraints

- Платформа — 8.3.27.x; режим сумісності розширення — `Version8_3_17` (не підвищувати). Методи новіші за 8.3.17 не використовувати.
- Формат вихідників — Designer platform XML під `СМП_ОнлайнОбменДанными/cfe/src`.
- Префікс імен нових об'єктів — `СМП_`. Імена: довідник `СМП_ПравилаСверки`, перелічення `СМП_ВидыПоказателейСверки`, загальний модуль `СМП_ОнлайнОбменСверка`, звіт `СМП_СверкаДанныхОбмена`.
- Мова коду, синонімів і повідомлень — російська (як у всьому розширенні); `НСтр("ru = '...'")` для текстів користувачу.
- Версія розширення: `3.2.0.4` → `3.3.0.1`.
- Контракт `/validate`: `Версия` = `1`; запит — JSON у gzip; відповідь — JSON без стиснення, `application/json; charset=utf-8`; ключі — російською. Коди: `200`, `400`, `404`, `422`, `500`.
- Вирази показників — лише `Вычислить` у безпечному режимі (`УстановитьБезопасныйРежим(Истина)`), без `Выполнить`.
- Автотестів у ітерації 1 немає (рішення автора). Перевірка — валідація Уніки, `operation=build`, `operation=syntax`, ручні контрольні точки (КТ) людини.
- Сховище — тільки читання; агент пише лише в базу агента `unf_test_claude`. `git push`, PR — лише на прохання людини.
- Явні права в ролі й команди у формах ПКО / облікового запису — **не робимо** (наступна ітерація).

## Review Focus

1. **Старий приймач без `/validate`** (платформний `404` з HTML) — очікується статус «Ошибка запроса» з текстом «…обновите расширение в приемнике», а не «нет учетной записи» і не падіння звіту. Перевірка — КТ2, сценарій 9 (Task 5).
2. **Порожнє значення проти нуля** (`Неопределено` в одній базі, `0` в іншій) — розбіжність типів = «Расхождение показателей» (рішення: порожнє дорівнює лише порожньому). Перевірка — КТ2, сценарій 4.
3. **Період без документів** — порожній звіт без помилки й без жодного HTTP-запиту. Перевірка — КТ3, сценарій 3.
4. **Обліковий запис без адреси підключення** — зрозуміла помилка до будь-якого запиту, а не виняток Коннектора. Перевірка — КТ3, сценарій 4.
5. **Тип документа без ПКО або з кількома ПКО** — зрозуміла помилка «не найдено / несколько правил — не поддерживается». Перевірка — КТ3, сценарій 5.
