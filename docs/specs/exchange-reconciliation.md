# Інструмент звірки «відправлено ↔ отримано» — специфікація

> Стан: чернетка. Гілка — `feature/exchange-reconciliation`.
> Позначки як в [архітектурі](../architecture/README.md): **[код]**, **[автор]**, **[гіпотеза]**;
> для рішень — **[рішення]**, для відкритих питань — **[?]**.

## 1. Початковий опис

Нам потрібен якийсь інструмент, яким ми будемо звіряти - чи все "доїхало" з джерела до приймача. 
Це в першу чергу стосується документів. 
Наприклад, у джерелі, адміністратор раз у якийсь період хоче перевірити - чи всі документи мають "відповідники" у приймачі, та у якому вони стані. 
Бо зазвичай, співставлення документів йде "1 до 1" по унікальному ідентифікатору. Рідко коли 1 документ джерела перетворюється в 2 документи на боці приймача.
В першу чергу треба перевірити наявність цих документів та в якому вони стані - записаний/проведений/помічений на видалення.
В другу чергу хотілося б розуміти картину по ключовим реквізитам документів. Наприклад: чи сівпадають суми та суми ПДВ, чи всюди заповнена номенклатура, хаарктеристики, партії, ціни, знижки і т.д.

## 2. Користувачі й сценарії

| Хто | Коли користується | Що хоче отримати |
|---|---|---|
| Розробник правил / налагоджувач обміну | періодично, зазвичай раз в місяць перед проведенням "Закриття місяця" | Хоче отримати впевненість, що все відтрансльовано в приймач|
| Кінцевий користувач (згодом) | те саме | те саме |

## 3. Що звіряємо

- **Об'єкти:** документи **[рішення]**. Довідники — поза першою ітерацією.
- **Еталонний набір:** документи джерела за період, що проходять ПРД облікового запису —
  тип з `ОбъектыКВыгрузке`, дата ≥ `ДатаНачалаВыгрузкиДокументов`, СКД-відбір **[рішення]**.
- **Ключ зіставлення:** GUID джерела = GUID приймача (ПКО з `СинхронизироватьПоИдентификатору`,
  див. [04](../architecture/04-pryiom.md#прочитатьобъект--один-обєкт)) **[рішення]**.
  ПКО з пошуком за полями (номер + дата) — поодинокі **[автор]**, поза першою ітерацією.
- **Розбіжності першої ітерації [рішення]:**
  - документа немає в приймачі;
  - стан відрізняється: записаний / проведений / помічений на видалення. Проведений у джерелі
    має бути проведений у приймачі; правил, що свідомо не проводять, немає **[автор]**.
    Непроведений через помилку проведення — розбіжність, з якою розбирається розробник;
  - не збігаються суми (сума документа, ПДВ) — механізм налаштування див. питання 8.
- **Період:** зазвичай місяць, перед закриттям місяця.

## 3а. Правила звірки (показники)

**[рішення]** Показники задаються правилами звірки на рівні ПКО (варіант Б, питання 8):

**[рішення]** `Справочник.СМП_ПравилаСверки`, власник —
`ПравилаКонвертацииОбъектов`, без ієрархії.

| Поле | Тип | Зміст |
|---|---|---|
| Код | Рядок 50, унікальний в межах ПКО, без автонумерації | Ідентифікатор показника для контракту (`СуммаНДС`) — за аналогією з кодом ПКО |
| Найменування | Рядок 100 | Назва для звіту («Сума ПДВ») |
| `Вид` | Перелічення `СМП_ВидыПоказателейСверки`: `Реквизит`, `Выражение` | Суми колонок ТЧ — виразом, окремого виду немає |
| `Реквизит` | `СправочникСсылка.Свойства` | Вибір зі списку реквізитів (див. нижче) |
| `Выражение` | Рядок необмежений | Для `Вычислить`; змінна контексту — `Объект` |
| `Допуск` | Число 15.2 | Допустима різниця для чисел (округлення ПДВ по рядках / від підсумку, валюта); 0 — точний збіг (типово). Копійчані розбіжності на практиці бувають **[автор]**; для порівняння береться допуск з правила джерела **[рішення]** |
| `Информативный` | Булево | Лише виводиться у звіт, у розбіжності не потрапляє (напр. посилання — контрагент) |
| `Порядок` | Число | Порядок колонок у звіті |
| `Отключить` | Булево | Як у ПКС: вимкнути, не видаляючи |
| `Комментарий` | Рядок | |

- **Вибір реквізиту:** список `Справочник.Свойства` з відбором за власником і
  `Вид = СМП_ВидыСвойств.Реквизит`. Власник — об'єкт **своєї** бази: в обліковому записі
  `ДляОтправки` — `ПКО.Источник`, у `ДляПолучения` — `ПКО.Приемник`. Значення показника —
  реквізит з ім'ям із найменування `Свойства`. Передумова: опис метаданих обох конфігурацій
  завантажено (`ЗагрузкаСтруктурыКонфигурации`).
- **Показник-посилання [рішення]** має бути інформативним. Для `Вид = Реквизит` — перевірка
  при записі елемента: посилальний тип у `Свойства.Типы` без `Информативный` — відмова.
  Для `Вид = Выражение` тип відомий лише при обчисленні — помилка на показнику під час звірки.
- **Контекст виразу:** `Объект` — `ДокументОбъект` (`Ссылка.ПолучитьОбъект()`); на сотнях
  документів прийнятно, ТЧ з `Итог`/`Выгрузить` доступні.
- **Форма елемента:** звичайні поля; `Реквизит` або `Выражение` — залежно від `Вид`;
  вираз — багаторядкове поле (без `СМП_РедакторКода`).
- **Права й навігація:** довідник — у роль `ПолныеПрава`; команда в панелі навігації форми
  ПКО поруч із ПКС і ПКЗ (`StandardCommand.OpenByValue`).

- Правила живуть **в обох базах**; кожна рахує показник за своїм правилом.
- Розходження правил звірки з ПКС і між базами **свідомо допускаємо**; синхронізація
  (перенесення через XML правил) — наступна ітерація.
- **Схема взаємодії [рішення]:**
  1. Джерело вибирає еталонний набір за період (розділ 3) і рахує свої показники.
  2. Джерело надсилає приймачу запит: **код ПКО + список кодів показників + список GUID**
     (по групі на кожен ПКО).
  3. Приймач за кодом ПКО визначає тип документа й свої правила звірки, шукає документи за
     GUID і повертає на кожен GUID: тип, номер, дату, `Проведен`, `ПометкаУдаления`, значення
     показників; документа немає — позначка «не знайдено»; показник без правила в
     приймачі — позначка «не налаштовано».
  4. Джерело зіставляє відповідь зі своїм набором і будує звіт.
- **Значення показників [рішення]:** примітиви (число, рядок, дата, булево) передаються як є;
  посилання — рядком-представленням і порівнюються лише як інформативні.

## 3б. Контракт `/validate/{ИдентификаторОбмена}`

**[рішення]** `POST /hs/smp_exchange/validate/{ИдентификаторОбмена}` HTTP-сервісу
`СМП_ОбменДанными`. Один ПКО на запит (звіт працює з одним типом документа; великі набори
діляться на порції за GUID). Ключі JSON — російською, як у пакетах обміну.

**Запит** — JSON у gzip (як `/data`):

```json
{
  "Версия": 1,
  "ИмяПравила": "РасходнаяНакладная",
  "Показатели": ["Сумма", "СуммаНДС"],
  "Объекты": ["9f1c…", "a27b…"]
}
```

**Відповідь `200`** — JSON без стиснення **[рішення]**:

```json
{
  "Версия": 1,
  "ИмяПравила": "РасходнаяНакладная",
  "Объекты": [
    { "УникальныйИдентификатор": "9f1c…", "Найден": true,
      "Тип": "Документ.РеализацияТоваровУслуг", "Номер": "БП-000123", "Дата": "2026-09-14T10:20:00",
      "Проведен": true, "ПометкаУдаления": false,
      "Показатели": {
        "Сумма":    { "Значение": 1200.00 },
        "СуммаНДС": { "Ошибка": "Поле объекта не обнаружено (Товары)" },
        "Скидка":   { "НеНастроен": true } } },
    { "УникальныйИдентификатор": "a27b…", "Найден": false }
  ]
}
```

**Коди:** `404` — немає облікового запису (як `/data`); `422` — немає ПКО з таким кодом;
`400` — тіло не розбирається. Тіло помилки — JSON, щоб джерело відрізняло наш `404` від
платформного (у старому приймачі без `/validate` — HTML) і писало «оновіть розширення в
приймачі». Помилки окремих показників — у тілі `200`.

**Версія контракту [рішення]** — поле `Версия` в запиті й відповіді, перша версія — `1`. Приймач,
що не знає версії запиту, відповідає помилкою з підтримуваною версією; джерело так само
перевіряє відповідь. Версія піднімається лише при несумісних змінах (перейменування,
видалення, зміна сенсу поля); нові необов'язкові поля — без зміни версії, невідомі поля
ігноруються. Не плутати з версією розширення.

## 4. Джерела даних

- Дані об'єктів у джерелі — запит у базі, де запускається звірка.
- Дані об'єктів у приймачі — **новий метод HTTP-сервісу `СМП_ОбменДанными`** **[рішення]**:
  за кодом ПКО, кодами показників і списком GUID повертає стан документів і значення
  показників (схема — розділ 3а).
- Стан черг — не потрібен для першої ітерації **[гіпотеза]**; може знадобитися, щоб
  пояснювати розбіжність («документ ще в черзі»).
- Правила конвертації — тип приймача з ПКО; налаштування сум — питання 8.

Звіт про розбіжності **[рішення]**. Без дій над ними: важливий сам факт розбіжності, кожну
розбирають вручну **[автор]**.

## 6. Де живе інструмент

**[рішення]** Звіт на СКД `Отчет.СМП_СверкаДанныхОбмена` у розширенні `СМП_ОнлайнОбменДанными`; запускається в
базі-джерелі.

- **Параметри:** обліковий запис обміну (`ДляОтправки`), тип документа — з увімкнених в
  обміні (`ОбъектыКВыгрузке`), період вибірки.
- **Розподіл коду [рішення]:**
  - `СМП_ОнлайнОбменСверка` — уся логіка: показники, еталонний набір, запити порціями,
    зіставлення, порівняння, статуси; на виході — готова таблиця. Там же — обробка
    `/validate` у приймачі;
  - модуль об'єкта звіту — лише `ПриКомпоновкеРезультата`: параметри → функція модуля →
    таблиця як зовнішній набір → виведення;
  - модуль форми звіту — лише інтерфейс: список вибору типів документа, відбір облікових
    записів `ДляОтправки`;
  - модуль HTTP-сервісу — тонкий обробник `/validate`, що делегує в модуль.

  Логіку без змін можна буде викликати з фонового завдання й покрити тестами.
- **Дані:** один готовий зовнішній набір даних СКД — дані джерела й відповідь
  `/validate/{Ид}`, уже зіставлені й порівняні в коді. Заповнюється в
  `ПриКомпоновкеРезультата`. Деталі — етап 6 у розділі 10.
- **Результат:** табличний документ. Показники — угруповання колонок (крос-таблиця);
  розбіжності — умовним оформленням; «лише розбіжності», відбори, сортування — налаштуваннями
  й варіантами звіту; розшифровка відкриває документ джерела.
- **Правила звірки:** окремий довідник, підпорядкований ПКО **[рішення]**.
- **Сервіс приймача:** новий ресурс `/validate/{Ид}` HTTP-сервісу `СМП_ОбменДанными`; приймач
  знаходить обліковий запис `ДляПолучения` за `ИдентификаторОбмена` — за аналогією з
  `/data/{Ид}` **[рішення]**.

## 7. Нефункціональні вимоги

- Обсяги: сотні документів на обмін за місяць **[автор]**.
- Права доступу й безпека (див. [91](../architecture/91-bezpeka.md)): новий метод сервісу
  віддає дані приймача назовні. Код по HTTP не передається: приймач рахує показники за
  власними правилами звірки (питання 12).
- Сумісність: УНФ, BAS УНФ, УТ, BAS Бухгалтерія; режим сумісності 8.3.17.
- Вплив на робочий обмін **[рішення]**:
  - документи «в дорозі» (ще в чергах) окремо не контролюються — звірку за потреби
    запускають повторно;
  - запит до приймача ділиться на порції по N GUID (10–50); розмір порції — параметр звіту;
  - ліцензії / сеанси приймача — не принципово **[автор]**;
  - тайм-аут запиту `/validate` — параметр звіту (СКД), окремо від робочого обміну.
- Вирази показників:
  - помилка обчислення показника — позначка на цьому показнику, відповідь не ламається
    **[рішення]**;
  - гарантовано обмежити довільний код лише читанням платформа не дає: безпечний режим
    запис у базу не забороняє. Загроза — помилка автора правила, не зловмисник (вирази
    живуть у базі, по HTTP не приходять);
  - **[рішення]** вираз обчислюється `Вычислить` у безпечному режимі
    (`УстановитьБезопасныйРежим(Истина)`); транзакцію з відкатом не використовуємо;
  - обмеження виразу: одне значення, без операторів, циклів і змінних. Доступні реквізити,
    функції й методи, що повертають значення, `?(…)`, `Новый`; процедури (`Записать()`)
    недоступні — це й захищає від випадкового запису. Сума з відбором рядків — через
    `Объект.<ТЧ>.Выгрузить(Новый Структура(...)).Итог("<Колонка>")`;
  - що не вміщається у вираз (цикл з накопиченням, запит до інших таблиць) — експортна
    функція загального модуля, яку викликає вираз; це зміна коду, не налаштування.
    Вид «код» через `Выполнить` — не в першій ітерації;
  - у безпечному режимі заборонено вмикати привілейований режим: функції БСП, що роблять це
    всередині, у виразі впадуть (позначка на показнику).

## 8. Поза межами

Наступні ітерації **[рішення]**:
- документ, що після відправки перестав проходити ПРД, але лежить у приймачі (зараз
  свідомо допускаємо);
- зворотна звірка: є в приймачі, немає в джерелі;
- ПКО з пошуком за полями (номер + дата), два ПКО на один тип джерела;
- випадок «замовлення УТ → передача товарів + чек / видаткова в УНФ» (алгоритм) — окремо;
- повнота заповнення реквізитів у приймачі (номенклатура, характеристики, партії, ціни,
  знижки);
- дії над розбіжностями (перевідправити, відкрити в приймачі).

| 15 | Що передавати як «типи»: типи приймача чи коди ПКО? | **[рішення]** Код ПКО + коди показників + GUID. |
| 16 | Код показника унікальний в межах ПКО? Які види показника? | **[рішення]** Унікальний в межах ПКО. Два види — реквізит і вираз; сума колонки ТЧ — вираз. |
| 17 | Що повертає приймач? | **[рішення]** GUID, тип, номер, дата, `Проведен`, `ПометкаУдаления`, показники; позначки «не знайдено» і «показник не налаштовано». |
| 18 | Ресурс сервісу: `/validate/{Ид}`, обліковий запис `ДляПолучения` за `ИдентификаторОбмена`? | **[рішення]** Так. |
| 19 | Де зберігати правила звірки: окремий довідник, підпорядкований ПКО, чи ТЧ ПКО? | **[рішення]** Окремий довідник, підпорядкований ПКО (як ПКС, ПКЗ). |
| 20 | Як показати результат? | **[рішення]** Табличний документ через СКД із зовнішніми наборами даних; інструмент — звіт, не обробка. Макет відкинуто: змінна кількість показників, відбори й оформлення — вручну. |

## 10. Етапи

> Імена об'єктів **[рішення]**: довідник `СМП_ПравилаСверки`, перелічення
> `СМП_ВидыПоказателейСверки`, загальний модуль `СМП_ОнлайнОбменСверка`, звіт
> `СМП_СверкаДанныхОбмена`.

### Ітерація 1 — наявність, стан, показники

0. **Підготовка.** База агента `unf_test_claude` з розширенням уже є (розширення ≡ `master` ≡
   сховище v78, станом на 2026-10-01). Перед кодом — `kit sync` без `-Apply`: чи немає нових
   версій у сховищі.
   **[рішення]** Перевірка — «петлею» в одній базі, потім на реальній парі **УНФ → БП**.
   Петля: у базі агента два облікові записи з однаковим `ИдентификаторОбмена` —
   `ДляОтправки` і `ДляПолучения`, адреса підключення — та сама база. У записі
   `ДляПолучения` — ПКО з тими самими кодами, `ТипПриемника` = тип документа УНФ (тотожне
   правило), тож приймач знаходить той самий документ за GUID. Розбіжності імітуються
   налаштуваннями: різні вирази показника з одним кодом у двох записах — «не збігається»;
   показник без правила в приймачі — «не налаштовано»; ПКО приймача з іншим типом
   документа — «не знайдено».
   Передумова: публікація бази агента на веб-сервері — робить людина **[автор]**.
1. **Контракт `/validate/{Ид}`** — розділ 3б.
2. **Довідник правил звірки** — структура, форма, права, навігація: розділ 3а.
3. **Обчислення показників** **[рішення]** — новий серверний загальний модуль
   `СМП_ОнлайнОбменСверка` (без виклику сервера; один на етапи 3–5).
   `ВычислитьПоказатели(Объект, Правила)` — спільна для обох боків, повертає
   «код → { Значение } | { Ошибка }»:
   - `Реквизит` — `Объект[<ім'я реквізиту>]` у `Попытка`;
   - `Выражение` — `Вычислить` в окремій функції з безпечним режимом;
   - помилка одного показника не зупиняє решту;
   - нормалізація для JSON: число, рядок (`СокрЛП`), булево — як є; дата — ISO;
     `Неопределено`/`Null` — `null`; посилання та інше — `Строка(Значение)`.

   Порівняння — лише в джерелі: число — `|джерело − приймач| ≤ Допуск` (допуск — з правила
   джерела); рядок — після `СокрЛП`; дата, булево — точно; різні типи —
   розбіжність; `Информативный` — не порівнюється.
4. **Приймач: ресурс `/validate/{ИдентификаторОбмена}`** у `HTTPServices/СМП_ОбменДанными`
   **[рішення]**:
   1. обліковий запис — `ПолучитьУчетнуюЗаписьОбменаПоИд(Ид, ЭтоПриемник = Истина)`, як у
      `/data`; немає — `404`;
   2. тіло: gzip → JSON; не розбирається — `400`;
   3. невідома версія — `400` з `"ПоддерживаемыеВерсии": [1]`;
   4. ПКО: власник — обліковий запис, код — `ИмяПравила`, не помічений на видалення; тип —
      `Тип(ПКО.ТипПриемника)` (рядок `ДокументСсылка.…`, як у конвертації); немає ПКО або
      тип не документ — `422`;
   5. правила звірки: власник — ПКО, коди з `Показатели`, `Отключить = Ложь`; коду без
      правила — `НеНастроен`;
   6. стан — одним запитом на порцію (`Номер`, `Дата`, `Проведен`, `ПометкаУдаления`,
      `Ссылка В (&Ссылки)`; посилання — `ПолучитьСсылку(Новый УникальныйИдентификатор(GUID))`);
      немає в результаті — `"Найден": false`; некоректний рядок GUID — `"Ошибка"` на цьому
      об'єкті, решта порції обробляється;
   7. показники — лише для знайдених: `ПолучитьОбъект()` → `ВычислитьПоказатели` (етап 3);
   8. відповідь `200`, `application/json; charset=utf-8`;
   9. непередбачена помилка — `500` з JSON-тілом і запис у журнал реєстрації. Інших записів
      у журнал немає (як і в `/data`).
5. **Джерело: збір даних [рішення]:**
   1. ПКО облікового запису з `ТипИсточника = "ДокументСсылка.<Тип>"`, не помічений на
      видалення; кілька ПКО на тип — звіт зупиняється з помилкою «не підтримується»
      (розділ 8);
   2. еталонний набір — документи типу за період з `Дата ≥ ДатаНачалаВыгрузкиДокументов`
      (реквізит шапки облікового запису), що проходять СКД-перевірку ПРД
      (`ПроверитьОбъектПоУсловиямОтбора`, див.
      [02](../architecture/02-vidpravka.md#реєстрація-документа)); помічені на видалення —
      включаються (помітка теж має доїхати);
   3. стан — одним запитом; показники — `ВычислитьПоказатели` за правилами звірки ПКО
      джерела (`Отключить = Ложь`); їхні коди — `Показатели` запиту;
   4. запит — порціями по N GUID, `POST <адреса>/hs/smp_exchange/validate/<Ид>`; адреса й
      Basic-авторизація — з `ПолучитьНастройкиТранспортаОбменаДанными`, як у
      `СМП_СобытияОтправкиДанных`; тайм-аут — параметр звіту (робочий обмін шле з
      `Таймаут = 0`);
   5. помилка транспорту або відповідь не `200` на порції — документи порції отримують
      позначку «помилка запиту» з текстом, решта порцій обробляється;
   6. результат — дві таблиці значень (джерело, приймач) для зовнішніх наборів СКД.

   Виконання — синхронно при формуванні звіту; фонове завдання — наступна ітерація.
   Примітка: СКД-перевірка ПРД — по одному документу (`ПараметрСсылка`); на сотнях
   документів прийнятно, на більших обсягах — перебудувати на список посилань.
6. **Звіт на СКД** `СМП_СверкаДанныхОбмена` **[рішення]**:
   - **набір даних** — один зовнішній, готовий: порівняння вже зроблене в коді (етап 3),
     СКД лише показує. Рядок — «документ × показник»; документ без показників — один рядок
     з порожнім показником;
   - **поля:** `Документ` (розшифровка), `Номер`, `Дата`; `ПроведенИсточник`,
     `ПометкаУдаленияИсточник`; `Найден`, `НомерПриемник`, `ДатаПриемник`,
     `ПроведенПриемник`, `ПометкаУдаленияПриемник`; `Статус`; `Показатель`, `Порядок`,
     `ЗначениеИсточник`, `ЗначениеПриемник` (рядком), `Расхождение`, `Информативный`,
     `Ошибка`;
   - **`Статус`** — рівня документа, перший, що підходить:

     | Статус | Коли |
     |---|---|
     | Помилка запиту | порція не отримала відповіді |
     | Не знайдено | документа немає в приймачі |
     | Стан відрізняється | проведення або помітка на видалення різні |
     | Розбіжність показників | хоч один неінформативний показник поза допуском |
     | Показник не перевірено | `Ошибка` або `НеНастроен` хоч на одному показнику |
     | Збігається | решта |

   - **параметри:** `УчетнаяЗапись` (лише `ДляОтправки`); `ТипДокумента` — рядок
     `Документ.…` зі списком вибору з `ОбъектыКВыгрузке.ПолноеИмяОбъекта` обраного запису
     (код у формі звіту); `Период`; `РазмерПорции` = 50; `Таймаут` = 60 с;
   - **варіанти:** «Розбіжності» (типовий, `Статус ≠ «Збігається»`) і «Усі документи».
     Рядки — документи зі станом, колонки — показники (крос-таблиця: значення джерела /
     приймача), `Расхождение` — червоним умовним оформленням.
7. **Перевірка [рішення]:**
   1. статична — валідація Уніки (метадані, форми, СКД, роль) і синтаксис BSL;
   2. `operation=build` у базу агента;
   3. петля (після публікації бази агента), сценарій на кожен результат:

      | Сценарій | Як отримати | Очікувано |
      |---|---|---|
      | Усе збігається | однакові правила в обох записах | Збігається |
      | Сума розійшлась | у приймачі `Объект.СуммаДокумента + 1` | Розбіжність показників |
      | Копійки в межах допуску | у приймачі `+ 0.01`, допуск 0,01 | Збігається |
      | Немає правила в приймачі | показник лише в записі джерела | Показник не перевірено |
      | Помилка виразу | вираз з неіснуючим реквізитом | Показник не перевірено |
      | Документа немає | ПКО приймача з іншим типом документа | Не знайдено |
      | Приймач недоступний | хибна адреса або тайм-аут 1 с | Помилка запиту |
      | Посилання без «Інформативний» | правило з реквізитом `Контрагент` | відмова при записі |

   4. реальна пара УНФ → БП — ручна перевірка автора, зокрема «Стан відрізняється»
      (у петлі не імітується: джерело й приймач — той самий документ);
   5. автотестів у першій ітерації немає — лише ручна перевірка; контур тестів (YaXUnit) —
      пізніше;
   6. версія розширення — 3.2.0.4 → **3.3.0.1**;
   7. документація: новий `docs/architecture/07-zvirka.md`; оновити `01` (довідник), `03`
      (ресурс `/validate`), README (карта документів);
   8. збірка `.cfe` у `build/artifacts/`.
